## The Technical Stack

The technical specs hold one stack document, `stack.md` at their root, laid out as a folder named for it where it holds more than one file unit ([`specs/methodology/spec-placement/where-a-file-goes.md § Where a File Goes`](/specs/methodology/spec-placement/where-a-file-goes.md#where-a-file-goes)). It says what the system is built with, what it relies on, and where its code lives. So each technology, and how the system uses it, has one home. A technical spec relying on a technology cites the stack document rather than introducing the technology where it is used ([`specs/methodology/sourcing-and-citation/one-home-per-fact.md § One Home Per Fact`](/specs/methodology/sourcing-and-citation/one-home-per-fact.md#one-home-per-fact)). The stack document holds a table of the system's parts and a table of what they rely on, and gives each technology in them with its version.

**The parts.** The table of the parts has one row for each part of the system: a user interface and a backend, say, or a single service. Its columns, in order:

| Column | Holds |
|---|---|
| Part | the part |
| Language | the language it is written in |
| Framework | the framework it builds on |
| Build Tool | the tools that build it, any tool generating files among them |
| Test Framework | the framework its tests are written in, the executable copies of the acceptance scenarios among them ([`specs/methodology/code.md § Tests`](/specs/methodology/code.md#tests)); a browser automation framework such as Playwright or Selenium for a user interface, say |
| Code Roots | the directories holding its code, its tests' directories among them |
| Excluded | the paths under its code roots that are not the application's own, code vendored from elsewhere or generated by a tool |

Each path is written from the project root, in backticks. A code root is never the project root itself, and never sits under another code root. So the specs and the working files stay outside the application's code, and no file is the code of two parts. The code roots, less what is excluded, name the application's code ([`specs/methodology/scope/what-spec-of-record-governs.md § What Spec of Record Governs`](/specs/methodology/scope/what-spec-of-record-governs.md#what-spec-of-record-governs)), so a check on code knows where to look, and a file outside them is no concern of [`specs/methodology/code.md`](/specs/methodology/code.md)'s rules.

**What the parts rely on.** The table of what the parts rely on is headed Technology, Kind and Purpose. It has one row for each technology the parts use in every environment, beyond the parts' own code, and each row says what the system uses the technology for:
- each database, with the purpose it serves, the core application's data or reporting, say;
- each cache, such as Redis or Memcached;
- each queue or stream;
- any other service of that kind.

A technology only some environments use is stated in those environments instead ([`specs/methodology/spec-placement/environments.md § Environments`](/specs/methodology/spec-placement/environments.md#environments)).
