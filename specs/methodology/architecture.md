## What the Methodology Holds

`specs/methodology/` holds the rules for writing the specs here, and for the code the specs govern. This overview also describes the skills that carry those rules out, and the code their scripts share ([`specs/methodology/spec-placement.md § What an Overview Describes`](/specs/methodology/spec-placement.md#what-an-overview-describes)). [`specs/architecture.md`](/specs/architecture.md) describes the specifications as a whole. The methodology's files hold:
- what the methodology governs, how an agent reads it, how the methodology governs itself, how each rule is enforced, how its instructions stay agnostic of the agent reading them, and the terms it gives meanings of its own;
- which skills belong to the methodology, how a skill is authored, and how the agent in use is set up;
- which spec a fact belongs in, at which altitude and in which file, what an overview describes beyond its directory, and the persona that each spec, the documentation and the code the specs govern are written as;
- how a capability domain is named, how a product file names the technical files behind it, and what a product module is and what a change to its code reads;
- where and in what form an open question is recorded, with its provisional answer, which the specs move forward on, and its impacts, everything relying on it;
- that a spec of a system that exists states the system as built, and records a suspected defect as an open question;
- what the technical stack and the environments hold;
- where a fact has its one home, how many rules a sentence states, which citations are allowed, how a section is titled and cited, how an outside standard the canon relies on is registered and cited, and how a materialized view is kept in sync with its sources and a product spec aligned with its technical counterpart;
- when a structured construct is required instead of prose, and which one, each construct adopting an outside standard whole where one meets its need;
- how one construct hands its work to another, and how a construct reads time;
- how a field is written, and how a diagram is drawn and sourced;
- how an expression that a construct computes or tests is written in FEEL, adopted whole, where a system's own arithmetic, in its precision, rounding and decimal places, and a month's end depart from FEEL; and the canon's own functions, written in FEEL where FEEL's built-in functions meet no need;
- when a capability owes acceptance scenarios;
- what a finished spec reads like and the trade-off that belongs in one, the clear prose it is written in, where an example is drawn from, how a number is used, and how Markdown, a bold lead-in, emphasis and literal text are written;
- the order a design's work takes, how a design's kind sizes its reviews, how the kinds of the files it changes pick its audit, how a review's reasoning effort is applied, and the one standard brief that starts each adversarial and post-apply review;
- the working files, the kinds of file a design is bounded to, and how a steer the user gives a design is recorded, typed and revisited;
- the rules that reach the code the application specs govern.

## The Methodology Governs Itself

The methodology is held to the rules it states. A rule reaches a methodology file unless the rule itself scopes it away, as the rules on acceptance scenarios and on `technical-specs` front matter do. `code.md`'s rules scope it away too, since they reach only code ([`specs/methodology/scope.md § The Methodology Governs Itself`](/specs/methodology/scope.md#the-methodology-governs-itself)).

## How the Rules Relate

The detail files that govern what a spec says, and the one that governs code, depend on one another. Each answers a question another leaves open. They apply to different subsets of what is written here. `specs/methodology/index.md` lists what each contains, and this section says how they fit together.

**The scope frames all of them.** Every rule here applies within it:
- `scope.md` states which files these rules reach and the shape of that scope, and how an agent loads what a step needs. It also states how the methodology governs itself, how rules and skills relate, how every rule is enforced, and how the methodology's instructions stay agnostic of the agent reading them.
- `skills.md` states which skills belong to the methodology, how a skill is authored, and how the agent in use is set up to carry out what the methodology leaves to it.
- `glossary.md` states the terms the methodology gives meanings of its own, how an entry is written, and where an abbreviation may be used.

**Placement comes first and constrains everything after it.** `spec-placement.md` settles which spec a fact belongs in, at which altitude, in which file. Nothing downstream can be decided before that. A citation cannot be written until there is a file to cite, and a capability cannot owe scenarios until it is known to be a product capability. `spec-placement.md` also sets what an overview describes beyond its directory, how a capability domain is named, how a product file names the technical files that build it, what a change to a product module's code reads, and what the technical stack and the environments hold.

**A persona for the methodology, the documentation, the application specs and their code.** `spec-placement.md` also gives a persona to each of the methodology, [`specs/architecture.md`](/specs/architecture.md), the documentation, the product specs, the technical specs and the code they govern. Each is written as its persona, and the adversarial review and the post-apply review of a design changing one are each framed as that persona.

**Sourcing and citation depends on placement and feeds back into it.** `sourcing-and-citation.md` governs where a fact lives, how everywhere else points at it, by a citation to a stable heading and never by direction, and what happens afterward when the fact changes. It holds a sentence at a rule's home to one rule, so a change to one rule edits no sentence stating another. It governs forms too. A form is defined once, and each use is an instance of it. A form adding to another is a sub-definition of it, and a point-of-use citation is composition by reference. It also governs how an outside standard the canon relies on is registered: each standard's record is held in `external-references.md`, and each section adopting the standard cites it. Its layering rules are stated in terms of the directories placement defines. The dependency runs both ways in one respect: deciding a fact's one home is a placement decision made under a sourcing rule. That is why the two are the pair most often consulted together.

A fact stated once is often restated elsewhere: in a directory's `architecture.md`, or in a diagram wherever it sits. In what it restates, each is a materialized view of the fact's one home, never its source. The home and its views work together. A diagram cites the home of everything it draws, and each home names the diagram back. A product spec and its technical counterpart are kept in sync another way. They are two drawings of one subject, each from its own perspective, and neither is a summary of the other. They are kept aligned. None of these keeps itself current, so each is a place to revisit when a change reaches it. That obligation outlasts the writing of the file.

**Modeling constructs cut across both.** Whether a passage is prose or a construct is independent of which spec it sits in or how it is cited. `modeling-constructs.md` applies wherever a rule, a process, an entity's behavior, an entry recorded repeatedly or a closed set a spec defines is described: at any altitude, in either half of `specs/application/`, and in these files and [`specs/AGENTS.md`](/specs/AGENTS.md). It reaches the working files too: its Record Form, and a Decision Table or a State Machine a design's Objective adds or rewrites, stated whole. What it tests is a rule's shape, never how the rule reads, and, for a table's construct, what the table is there for. Prose holds only the simplest rules, and its choosing table picks the construct for the rest.

Each construct but the Record Form and the Basic Table adopts an outside standard whole, registered in `external-references.md`. The Decision Table is DMN's DecisionTable; the State Machine, UML's StateMachine; the Algorithm and the DAG, UML's Activity; and the Constraint, UML's Constraint. Each means what its standard says, with each departure named and why it was needed, and each writes its expressions in FEEL as `expressions.md` states it. A construct is chosen over prose however rarely its case appears, and it adopts a notation an engineer already knows before the canon invents one. The worked examples sit apart, in `examples/`, a tree named broad to narrow by subject and topic, so an agent loads one only when a step needs it. The constructs and the Record Form apply `sourcing-and-citation.md`'s rule that a form is defined once and each use is an instance of it.

`modeling-constructs.md`'s definitions relate as classes do. Construct is the abstract root. Every other definition but an interface extends one base, and an interface extends only interfaces. A definition implements interfaces by citing them, and the interfaces include being declared, ordered, configured or keyed. Every reference to a definition is a citation. In a tabular construct, a column headed by a field label is a field of each row, as every column of a Basic Table is. Each other header says what its column represents. A construct that extends another is a sub-definition of it. An instance of a construct implementing Configured Construct is a configured instance when its rows, states or steps are data the system's users change. The tables written are then an example of that data. `modeling-constructs.md` also defines the Fact record type for a fact several constructs test, and says how one construct hands its work to another.

`modeling-constructs.md` sets the form of a field too, wherever the field is written, and of a block of fields and a record, one a field holds among them ([`specs/methodology/modeling-constructs.md § Fields`](/specs/methodology/modeling-constructs.md#fields)). `spec-style.md` sets the rest of markup:
- [`specs/methodology/spec-style.md § Markdown`](/specs/methodology/spec-style.md#markdown) maps the canon's forms onto GFM's elements, and sets where a list item ends and how a fenced `markdown` block is read;
- [`specs/methodology/spec-style.md § Bold Lead-ins`](/specs/methodology/spec-style.md#bold-lead-ins) sets every other bold phrase opening a line;
- [`specs/methodology/spec-style.md § Emphasis`](/specs/methodology/spec-style.md#emphasis) and [`specs/methodology/spec-style.md § Literal Text`](/specs/methodology/spec-style.md#literal-text) set what italic and backticks mark;
- [`specs/methodology/spec-style.md § Blank Lines`](/specs/methodology/spec-style.md#blank-lines) sets where a blank line falls, so items of one kind stand together.

The Record Form gives the form of an open question, which `spec-placement.md` places, and the form of a design document's steering decisions. The diagram rules and the rule for citing a part of a keyed instance are where `modeling-constructs.md` depends on `sourcing-and-citation.md`, and they are read with that file.

**Acceptance scenarios reach the narrowest scope.** `acceptance-scenarios.md` applies only to a product capability's own section. That is the narrowest reach of the files that govern what a spec says. Its own text scopes it to product specs, which is why no technical file owes any.

**Code is reached by one file.** `code.md` holds the rules that reach the code the application specs govern: which code is governed and which is wiring, how governed code names the specs it carries out or checks, how it changes, and what a test is. Its annotation is a citation written as `sourcing-and-citation.md` gives it, without the backticks. No other file's rules reach code, except those `code.md` cites ([`specs/methodology/scope.md § What Spec of Record Governs`](/specs/methodology/scope.md#what-spec-of-record-governs)).

**Style applies last, and to every spec.** `spec-style.md` governs what any finished spec reads like, whatever the spec says and wherever it sits. Its clear prose and its rule on numbers also reach the agent instructions, the skills and the documentation. Its clear prose reaches the working files too. Each file is written for its primary reader.

**The order of a design's work.** `design-workflow.md` orders a design's work, from its goals and frame to its approval, and from its apply to its commit. It writes that order as the two State Machines a design's Status runs, and each state that does work cites the rule or the section doing it. It also says how a design's kind sizes its reviews, how the kinds of the files it changes pick its audit, and how a review's reasoning effort is applied, and it holds the one standard brief that starts each adversarial and post-apply review.

**Working files govern no spec.** `working-files.md` sets the form of the working files: a design document, a stamp and a follow-up. A design document is the plan for one change. It holds the goals the user agreed on for the change, the steers that shaped it, and its steps, each stating as its Objectives the states the applied work holds, never the text that brings them about. The user approves the plan, which authorizes the builder to write the text at the apply, and then approves the applied result. Each steer is a selection among the options the builder offered, or a perspective the user brought. Only the user revises a goal or a steer. The document's log records each check of its work with its counts by mark, and each event of its workflow, and the document names the designs it waits on and the wording it retires. A design's changes are the writing its steps reach and the direct edits and the user's own edits its log names, committed together. `working-files.md` also says how the builder changes a working file, which no design changes, how a design changing code differs, how a design whose record uses a form not yet applied is validated by hand, how a finding after the approval is settled, a tactical fix never sending a design back, what becomes of each change uncommitted in a design's checkout at each event of its work, how a design sent back keeps its changes, and how a design applies meanwhile, those changes stashed. A stamp records when a check passed. A follow-up holds work not yet done. Before each adversarial round and before the user's approval, the validation review, which the design script makes, checks the design document's structure, and stamps it on the way to the approval. No spec but `working-files.md` names a working file ([`specs/methodology/sourcing-and-citation.md § Which Citations Are Allowed`](/specs/methodology/sourcing-and-citation.md#which-citations-are-allowed)).

## How the Rules Are Applied

These files state the rules. The skills registered in [`specs/methodology/skills.md`](/specs/methodology/skills.md) apply them: they sequence the work, record what goes wrong, check the result, and teach the craft a rule assumes. Registration also marks the boundary between the methodology's skills and any other skill under `.ai/skills/`. No skill is a rule's home. Where a skill disagrees with a rule, the rule governs ([`specs/methodology/scope.md § Rules and Skills`](/specs/methodology/scope.md#rules-and-skills)).

**`design-specs` sequences these rules and carries what they cannot.** It gives each rule a change applies a point-of-use citation rather than restating the rule. Citing is the only way the skill can stay correct as these rules are amended. It forks on the kind of specification a change touches. What it adds is what no rule can hold: the failures that recur while the rules are applied, such as writing a fact before checking whether it already had a home. A rule states what correct looks like. `design-specs` records how people miss it.

**`audit-specs` checks whether these rules, and [`specs/AGENTS.md`](/specs/AGENTS.md)'s, actually held.** A script first decides what the files alone can decide. Reading audits, one per family of rules, judge the rest. For every section stating rules, `audit-specs` names the reading audit enforcing it, or names it a section stating operating rules. The skill steps that apply and cite such a section's rules check them. For a section of `code.md`, `verify-spec-implementation` names the check enforcing it instead, unless `audit-specs` names it a section stating operating rules ([`specs/methodology/scope.md § Rules and Skills`](/specs/methodology/scope.md#rules-and-skills)). So a rule that changes takes its check with it, and a finding points at the rule rather than only at a line.

What `audit-specs` leaves unaudited by choice, it declines by name rather than by silence.

**`author-mermaid-diagram` serves the diagram rules.** [`specs/methodology/modeling-constructs.md § Diagrams`](/specs/methodology/modeling-constructs.md#diagrams) licenses exactly one kind of rendering for a human reader. That section leaves where a diagram goes to the reader's need. It bounds a diagram's form, what the diagram may show, and how the diagram and its sources cite each other. The skill is how a diagram gets authored, rendered and checked, and that section points at the skill directly. The skill differs from `design-specs` and `audit-specs` in its subject, not in how it is governed. Drawing a good diagram is craft, so the skill cites these files only where they govern a diagram. `design-specs` and `audit-specs` exist to serve these rules, and cite them throughout.

**`configure-spec-of-record` sets up the agent in use.** The methodology's instructions name no agent, so the agent in use sets itself up, through that skill, for what only it can carry out. Applying a review's reasoning effort is among that work ([`specs/methodology/skills.md § Setting Up an Agent`](/specs/methodology/skills.md#setting-up-an-agent)). The skill writes only what it needs, outside the scope.

**`implement-specs` carries the specs into code.** It applies `code.md`'s rules: how governed code names what it carries out or checks, how it changes, and what a test is. It designs the code and its tests from one product module's specs, as a design document written as the software engineer would write it. It takes that design document through the same reviews as a design changing the specs, and the user approves the plan before any code is written. It then writes the code, runs the local environment's tasks, and checks its own work before the post-apply review reads it and `verify-spec-implementation`'s full run audits it.

**`verify-spec-implementation` checks the code against its specs.** It is to code what `audit-specs` is to the specs. A script checks the app-spec annotations and lists the spec sections no code cites. A cold reading judges whether each unit carries out what it cites, and whether code with no annotation is wiring. The cold reading also reads the technical overview's account of the code against the code. The skill only reads: the project's tests run where the project's own pipeline runs them.

**The code the skills' scripts share.** `.ai/skills/lib/` holds what the scripts of two skills both need, the design document tooling and the construct checks among it. The skills' entry scripts import each module ([`specs/methodology/skills.md § Authoring a Skill`](/specs/methodology/skills.md#authoring-a-skill)).
