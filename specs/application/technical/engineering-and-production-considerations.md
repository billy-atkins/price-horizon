## Engineering and Production Considerations

**Data pipeline cadence.** Syndicated and POS data are ingested in batch on a daily or weekly cycle. Price-change signals that matter for a fast-moving competitive response are ingested in near real time. The qualitative corpus is re-embedded on a periodic cycle as new documents arrive. The forecast materialization job ([`specs/application/technical/materialization-service/forecast-materialization.md § Forecast materialization`](/specs/application/technical/materialization-service/forecast-materialization.md#forecast-materialization)) is triggered by a competitor data refresh. Queries continue to use the last complete publication until its replacement succeeds.

**Latency and cost budget.** The scorecard and narrative layers need a response time in the low seconds to feel like a search box. The drill-down and full decomposition can tolerate more, since the user has already committed to exploring. The scoped parsing cache in [`specs/application/technical/guarantees-mechanics.md § How the Guarantees Are Achieved Mechanically`](/specs/application/technical/guarantees-mechanics.md#how-the-guarantees-are-achieved-mechanically) accelerates repeated interpretations. It does not weaken the guarantee that an uncached query still runs the full pipeline.

**API shape.** A single REST API serves both the answer surface and the control plane, with one auth model and one set of client libraries for both. The service boundary ([`§ Engineering and Production Considerations § Service boundaries`](#service-boundaries)) separates the two, not the API surface. [`specs/application/technical/query-service/intent-and-retrieval.md § Dynamic Retrieval and Weighting (when the question is asked) § Session context`](/specs/application/technical/query-service/intent-and-retrieval.md#session-context) states what a question request carries and what every answer returns about its business unit and kind of decision. JSON:API-style query conventions keep the answer surface from over-fetching a deeply nested response. `include=` pulls in related resources in one round trip, with dotted paths reaching into nested Positioning Candidates when needed (`include=positions.rationale,positions.simulatedOutcome`). `fields[type]=` sparse fieldsets avoid pulling a full Rationale Record when a caller needs only a few fields. The performance work happens in the data layer, not the API. The Effective Price Forecast already bundles the fact and its rationale into one read, so an include or a field selection serves already-joined data, not a chain of separate lookups.

**Deployment and versioning.** [`specs/application/product/platform-and-compliance-operations/deployment-topology.md`](/specs/application/product/platform-and-compliance-operations/deployment-topology.md) states the deployment topology and its per-business-unit configuration scoping. The business-unit-scoped rows of [`specs/application/technical/control-plane-service/control-plane.md § Control Plane § Configuration change path`](/specs/application/technical/control-plane-service/control-plane.md#configuration-change-path) are the technical-specific configuration surface underneath that same scoping. The mechanism itself stays canonical across every installation: the seeding and consolidation logic, and the reconciliation approach. Only its tuning is configuration.

The application and the models version independently of each other. The application version covers the orchestration, the positioning engine's logic, the reconciliation mechanism, the Event Type Taxonomy ([`specs/application/technical/data-model.md § Core Data Model § Pipeline and Answer Artifacts § Signal Routing Rule`](/specs/application/technical/data-model.md#signal-routing-rule)), the horizon set the grid materializes against, the connector built for each data source type, and the API and UI contracts. Each model and weighting rubric in the registry ([`specs/application/technical/model-registry.md § Model registry`](/specs/application/technical/model-registry.md#model-registry)) versions on its own cadence. Each is validated independently against the golden-question harness ([`specs/application/technical/evaluation-and-monitoring.md § Evaluation and monitoring`](/specs/application/technical/evaluation-and-monitoring.md#evaluation-and-monitoring)). A customer can take an application upgrade without any model changing underneath them. A customer can also receive a recalibrated model without an application upgrade forcing new UI or workflow changes on them at the same time. Acme AI ships each as its own release. A customer's installation pins to a specific application version and a specific version of every model it calls. The installation is upgraded Acme AI-managed or self-managed, as [`specs/application/product/platform-and-compliance-operations/versioned-upgrades.md § Versioned Upgrades`](/specs/application/product/platform-and-compliance-operations/versioned-upgrades.md#versioned-upgrades) describes.

### Orchestration

Once a question is asked, the live-path pipeline needs a workflow layer built for retries, partial failure, and observability, not a single long prompt. Each step in it is independently testable. The pipeline is a fixed, deterministic sequence with parallel fan-out and fan-in, not a graph where a model decides the next step. So the right category of tool is a durable execution engine built for retryable pipelines, not an agent framework. [`specs/application/technical/stack.md § Technical Stack`](/specs/application/technical/stack.md#technical-stack) names the engine. The engine runs both the query service's live path and the materialization service's batch path. The batch path runs on the cadence [`specs/application/technical/materialization-service/forecast-materialization.md § Forecast materialization`](/specs/application/technical/materialization-service/forecast-materialization.md#forecast-materialization) sets, and its runs start without any question being asked. Running both paths on the same orchestration engine is part of what keeps a live answer and a materialized one from ever disagreeing ([`specs/application/technical/materialization-service/forecast-materialization.md § Forecast materialization`](/specs/application/technical/materialization-service/forecast-materialization.md#forecast-materialization)). The two paths share one set of retry, failure-handling, and scheduling semantics, not separate tools whose behavior has to be kept in sync with each other.

### Service boundaries

The system runs as separate services, not one. A different property justifies each service, and none is split for its own sake. The query service runs the live path ([`specs/application/technical/query-service/intent-and-retrieval.md § Dynamic Retrieval and Weighting (when the question is asked)`](/specs/application/technical/query-service/intent-and-retrieval.md#dynamic-retrieval-and-weighting-when-the-question-is-asked), [`specs/application/technical/predict-computation.md § Predict Computation`](/specs/application/technical/predict-computation.md#predict-computation), and [`specs/application/technical/query-service/layered-output-synthesis.md § Layered Output Synthesis (producing the answer)`](/specs/application/technical/query-service/layered-output-synthesis.md#layered-output-synthesis-producing-the-answer)). It is request-driven and held to the latency budget. The materialization service runs the batch path: forecast materialization, driver signal extraction, and product and geography reconciliation. It is throughput-oriented and tolerant of long-running jobs, with nothing in common operationally with an interactive request. The control plane service is separated for a security reason, not a workload reason. Its write operations govern reference data, materiality thresholds and identity mappings. Its read-only operations inspect authorized administrative data. The service boundary isolates configuration writes from the query service. Only the control plane service holds write credentials to the reference tables in [`specs/application/technical/data-model.md § Core Data Model § Reference and Master Data`](/specs/application/technical/data-model.md#reference-and-master-data). The query service never does. So a vulnerability in the far larger, far more exposed query surface cannot reach the capability to change what a competitor's code means or what a business unit's threshold is. This is the mechanism behind the architectural separation [`specs/application/product/identity-and-access/using-and-administering-kept-apart.md § Using and Administering Kept Apart`](/specs/application/product/identity-and-access/using-and-administering-kept-apart.md#using-and-administering-kept-apart) states.

[`specs/application/technical/architecture.md § Architecture Overview § Diagrams § Layer Composition`](/specs/application/technical/architecture.md#layer-composition) and [`specs/application/technical/architecture.md § Architecture Overview § Diagrams § Trust Boundaries`](/specs/application/technical/architecture.md#trust-boundaries) render this.

### Security and governance

The primary control is deployment topology. Each customer's data stays inside the customer's own environment by construction. There is no shared store for it to leak through, save what the client lets a frontier model provider see ([`specs/application/technical/model-registry.md § Model registry`](/specs/application/technical/model-registry.md#model-registry)). Acme AI's access as the operator is a secondary, governed layer of access control and audit logging. It is not a substitute for the residency decision itself.

For federated business-unit access, IdP-asserted claims ([`specs/application/technical/identity-and-access.md § Business unit access, federated`](/specs/application/technical/identity-and-access.md#business-unit-access-federated)) are the enforcement boundary. Different services and different stores check them differently. In the vector database, the claims are checked by the per-namespace credentials [`specs/application/technical/secrets-management.md § Secrets management`](/specs/application/technical/secrets-management.md#secrets-management) issues the query service, over the namespaces [`specs/application/technical/data-model.md § Core Data Model § Harmonized quantitative foundation`](/specs/application/technical/data-model.md#harmonized-quantitative-foundation) partitions the vector database into. In the structured database and the materialized grid, they are checked by the claim filter that [`specs/application/technical/query-service/intent-and-retrieval.md § Dynamic Retrieval and Weighting (when the question is asked) § Intent parsing and decoupling`](/specs/application/technical/query-service/intent-and-retrieval.md#intent-parsing-and-decoupling) applies on every retrieval. At the control plane service, they are checked by the Control plane admin claim check [`specs/application/technical/identity-and-access.md § Business unit access, federated`](/specs/application/technical/identity-and-access.md#business-unit-access-federated) describes, behind the write credentials [`§ Engineering and Production Considerations § Service boundaries`](#service-boundaries) confines to that service. The installation checks the client’s current support permission on both federated and local emergency sign-in and on every subsequent privileged action under [`specs/application/technical/identity-and-access.md § Platform admin access`](/specs/application/technical/identity-and-access.md#platform-admin-access). Its break-glass credentials are held in the vault [`specs/application/technical/secrets-management.md § Secrets management`](/specs/application/technical/secrets-management.md#secrets-management) describes.

Competitor pricing intelligence and licensed syndicated data both carry real contractual and competitive sensitivity on top of that. Access control needs to reflect data licensing terms. Every generated answer needs an audit trail sufficient to defend it internally or to a retailer. [`specs/application/technical/architecture.md § Architecture Overview § Diagrams § Trust Boundaries`](/specs/application/technical/architecture.md#trust-boundaries) renders this.

An Audit Log Entry ([`specs/application/technical/data-model.md § Core Data Model § Audit Log § Audit Log Entry`](/specs/application/technical/data-model.md#audit-log-entry)) is application data, not a log in the observability sense. It never touches the observability pipeline that application logs flow through (this section's application logging passage).

A middleware component writes the entry. The pattern is the same by whichever name a given stack calls it: ASP.NET Core-style middleware or an Action Filter, or a Servlet Filter or Spring's HandlerInterceptor in a JVM stack. The middleware wraps every request in the same pipeline, whichever of these it is:
- a Query user's question, arriving through the UI or a direct API call
- a Control plane admin's or an Identity admin's change through the control plane service
- a Platform admin action against the query, materialization, or control plane service ([`§ Engineering and Production Considerations § Service boundaries`](#service-boundaries))

So no individual action's business logic needs to know it is being audited.

Onboarding, release activation, retention purge and external routing changes originate outside the request pipeline. Acme AI's provisioning tooling writes onboarding evidence in its own transaction. The purge run ([`§ Engineering and Production Considerations § Security and governance § Audit log purge`](#audit-log-purge)) writes a retention_purge entry. The control plane service reconciles client-owned routing revisions under [`specs/application/technical/control-plane-service/control-plane.md § Control Plane § External model routing changes`](/specs/application/technical/control-plane-service/control-plane.md#external-model-routing-changes).

The middleware commits the question_asked audit event before returning the response. When the selected or newly computed forecast forms part of the response, commit its Delivered Answer and the question link together. A failure before a forecast completes records the question without a delivery link. A Platform admin's read-only diagnostic action commits its audit entry independently.

After receiving the complete answer, the client acknowledges the delivery identifier under the original authenticated identity and unit. The service matches the receipt to that identity, unit and delivery before saving its first receipt time. Repeated acknowledgements return the recorded confirmation. A committed answer with no acknowledgement stays unconfirmed, including an older answer for which receipts were never collected. [`specs/application/product/platform-and-compliance-operations/onboarding-verification.md § Onboarding Verification`](/specs/application/product/platform-and-compliance-operations/onboarding-verification.md#onboarding-verification) uses that distinction to verify receipt.

An action may write something beyond its own Delivered Answer: onboarding, an upgrade, a configuration_changed edit against any of the self-service surfaces that [`specs/application/technical/control-plane-service/control-plane.md § Control Plane § Configuration change path`](/specs/application/technical/control-plane-service/control-plane.md#configuration-change-path) names, or a question answered by a live computation that also persists an Effective Price Forecast row. There, the audit entry joins the same database transaction as whichever of those writes applies. If the transaction fails to commit for any reason, the audit write included, the whole request rolls back together. An action and its own audit entry are never separated.

Some of a business unit's settings shape an answer: its dead-zone threshold, a materiality threshold, an archetype's display label, or the display name of one of its competitors, of one of its geographies or of the business unit itself. A configuration_changed entry against one of these settings is, on committing, what increments that business unit's `business_unit_configuration_version`. Every Effective Price Forecast row pins itself to that same version. Any other configuration_changed entry, among them one against a data source's credentials, a log threshold, a glossary alias or an IdP claim mapping, is audited the same way but raises no version ([`specs/application/technical/data-model.md § Core Data Model § Pipeline and Answer Artifacts § Answer Provenance`](/specs/application/technical/data-model.md#answer-provenance)). So every version bump is one specific, attributable audit entry, recording who changed what, from what value, to what value, and when. It is not just a number that changed.

Where the action is read-only, such as a diagnostic session, viewing application logs, or reading the pinned versions, the audit write is the only write in the request. It runs in its own transaction, and the response is gated on that write's success. A Query user's question served straight from the grid is never this case. Its Delivered Answer and its audit entry are a pair in one transaction, and they gate the response together, under the same guarantee.

If the audit write itself fails, the request fails outright, as any other failure to complete an answer already does ([`specs/application/product/trust-and-explainability/degraded-answer-behavior.md § Degraded Answer Behavior`](/specs/application/product/trust-and-explainability/degraded-answer-behavior.md#degraded-answer-behavior)). No forecast is shown. What is shown is that one could not be computed, and the Query user is told to try again. An answer is never shown with no audit trail behind it, and a stale or partial substitute is never offered in its place. Either way, an action can never be left recorded as having happened, or its results shown, with no audit trail behind it. Nor can an audit entry be left behind for a write that itself rolled back.

Holding the audit record as application data is a design choice. An audit record needs long retention, a stable and versioned schema, transactional certainty, and to stay queryable through the Control Plane's self-service surface. No general telemetry backend is built to provide these, whether OpenTelemetry-native or a client's own observability platform. Nor is the audit record ever held in a shared, Acme-AI-hosted store spanning multiple customers, by the same residency principle this section states.

The audit record is retained for at least one year by default. That year is a floor, and the installation-wide retention_period setting can be raised above it to meet a client's contractual requirement. A raise is recorded the same way as any other governed configuration_changed entry, and governed as [`specs/application/technical/control-plane-service/control-plane.md § Control Plane § Configuration change path`](/specs/application/technical/control-plane-service/control-plane.md#configuration-change-path) sets out. The handling of a requested decrease follows [`§ Open Questions [Name: Retention Decrease]`](#open-questions).

Both the client and Acme AI can read the audit record, but not through the same surface, and not everyone reads the same slice of the table. A Control plane admin views every entry scoped to their own business unit through the self-service Control Plane surface. That takes in Acme AI's own access to the business unit, every configuration_changed edit made within it whichever admin made it, and their own Query users' questions alike. Through the same surface, the Control plane admin also views an installation-wide entry, such as a Platform admin's upgrade or an Identity admin's change to who holds the Platform admin role. An Identity admin views every IdP claim mapping change across the installation, and every question denied because its asker's access held no business unit. The Identity admin views them through the same surface every other business-unit activity already goes through ([`specs/application/product/tenant-administration/audit-log-visibility.md`](/specs/application/product/tenant-administration/audit-log-visibility.md)). This is the mechanism behind that section's promise that the audit record is one a client can see, not one it must trust happens somewhere out of sight. Acme AI views its own access, every configuration_changed edit, and every business unit's Query user activity across the installation. It views them through its own internal engineering tooling, not through any PriceHorizon product screen. Platform admin's other activities, onboarding, upgrades and diagnostic access, already work outside the client-facing product entirely in the same way.

Further capabilities follow directly from fields already on the Audit Log Entry, not from any new mechanism. They exist so the audit trail can be used under pressure, not only consulted after the fact.

In production, compare two retained deliveries under [`§ Engineering and Production Considerations § Security and governance § Comparing two delivered answers`](#comparing-two-delivered-answers). A question that produced no delivery remains visible under the existing audit permissions and supplies no delivered figures for comparison.

Investigating a non-technical executive's complaint about what they were told never depends on recomputing anything. The Delivered Answer record captures directly what Position and Simulate produced, and the exact application and model versions that produced it, alongside the forecast reference and the rendered narrative, so every piece of one delivered answer lives in one row, referenced as a whole by `delivered_answer_id`. A question_asked entry's `delivered_answer_id` points to the one record holding every piece together. Nothing about a past answer ever needs to be recomputed to know what it was.

A retained record measured in years is only as useful as someone's ability to find one entry inside it. That is a narrower problem than a general log search engine solves, because every field on the Audit Log Entry schema is already structured: a foreign key, an enum, a timestamp. No field is an unstructured line of text parsed and indexed after the fact. The filters are actor, action_type, and occurred_at as a bounded time range. For a question_asked entry with a retained delivery, filter by the competitor on its forecast and the requested geography on the delivery. An unknown historical request geography cannot satisfy an exact geography filter. For a configuration_changed entry, they include its changed_field. Each of these filters is therefore ordinary indexed-column filtering against the same structured database the audit table already lives in. It matches ranges and exact values already known, not a purpose-built search index bolted on top. Keyword search uses the retained answer’s rendered_narrative. Selecting its delivery opens the submitted question under the existing audit-detail permissions.

A filtered view defaults to a recent window of thirty days, not the full retention period. It shows a visible count of matching entries by day across that window. So a reviewer sees where activity clusters before reading a single row, instead of only after stumbling onto it. A cluster might be a spike in outcomes of [`§ Engineering and Production Considerations § Orchestration § Question run [States.State: query_denied]`](#question-run), or several configuration_changed edits within the same hour. Bulk forecast review ([`specs/application/product/accuracy-governance.md § Tracking Forecast Accuracy`](/specs/application/product/accuracy-governance.md#tracking-forecast-accuracy)) shows a pattern across many forecasts at once, not one at a time, for the same reason.

Selecting an entry expands its full detail without losing the current filter. The detail holds the referenced Delivered Answer, with the original group order, labels, candidate figures, simulated outcomes, numeric-claim evidence and exact delivered narrative. It also holds a link into the evidence already exposed for its referenced forecast ([`specs/application/product/answer-engine/predict.md § Predict: what will the competitor do`](/specs/application/product/answer-engine/predict.md#predict-what-will-the-competitor-do)). That section's evidence drill-down already establishes the "without leaving the analysis" pattern. The audit detail extends the same pattern to an audit entry, instead of inventing one separately for it.

The filtered set can be exported to a flat file. The export holds exactly the rows matching, never a capped sample. A flat file is the form this record most often needs to take to leave the product. It is handed to an auditor, legal, or the client's own security team, none of whom need a PriceHorizon login of their own to receive it. The export never carries a referenced Delivered Answer's content, only the delivery identifier and, for a forecast-bearing entry, the forecast identifier obtained from that same unit's delivery. Entries without a forecast carry neither identifier. The Delivered Answer record exists because it restates an answer's protected substance directly, not by reference. A flat file leaving the product entirely is the uncontrolled destination that substance is never allowed to reach anywhere else in this design. The Delivered Answer's content stays viewable in place, through the governed surfaces this section describes. An export never carries it.

Application logging ([`specs/application/product/logging-and-traceability.md § Logging and Traceability § Application Log`](/specs/application/product/logging-and-traceability.md#application-log)) is a concern distinct from the audit log. It serves debugging why a step failed, not tracking who accessed what. It covers the application only. The infrastructure PriceHorizon runs on, the servers, network, and storage, is the responsibility of the client's own infrastructure team. That team monitors it with whatever tooling it already runs in the client's environment, since PriceHorizon is self-hosted inside that environment, never Acme-AI-hosted ([`specs/application/product/platform-and-compliance-operations/deployment-topology.md`](/specs/application/product/platform-and-compliance-operations/deployment-topology.md)).

The application's OpenTelemetry signals, its traces, logs and metrics alike, never carry the categories of protected content: a forecast's quantitative values, a Driver Signal's document content, credential material, or a raw IdP claim payload. Attribute an authenticated request to its actual actor and authorized scope. A scheduled or background job carries its service identity, business unit where applicable and run identifier. A job started by an administrator also retains the authorized initiating identity. Every entry and trace carries the application_version that produced it. That version keeps changing over successive releases, and a log line without it cannot be placed against the release that behaved that way.

PriceHorizon provides no product screen for reading application log content. A Control plane admin can raise the threshold that controls how much gets captured ([`specs/application/product/tenant-administration/application-log-control.md`](/specs/application/product/tenant-administration/application-log-control.md)), but never reads the resulting content. Reading it is not what the Control plane admin's self-service surface is for.

The application writes its structured log lines, spans and metrics to standard output or a log file. That is the ordinary mechanism for a self-hosted application, not a custom export path of its own. A standard forwarding agent deployed within the installation tails that output and forwards it to whatever observability platform the client already runs. Acme AI stands up no redundant tool inside an environment the client already instruments. This extends the same reasoning, that the client already has infrastructure tooling of its own, to the application layer. Where a client has no platform of their own, the same agent forwards instead to a self-hosted, OpenTelemetry-compatible viewer, shipped alongside PriceHorizon as the fallback default. Either way, PriceHorizon requires no connection outside the client's own environment. Where the client's own platform runs is the client's choice. PriceHorizon never sends any of this output to anything Acme AI hosts, and never combines it with another customer's.

How Acme AI engineering gets access to view the output differs by which path applies. So does what PriceHorizon's audit trail can see of that access. Where the output goes to the client's own platform, whatever the client grants there is the client's own process. That process is outside PriceHorizon's access model to define, and outside its Audit Log to observe. PriceHorizon has no visibility into an access that never touches it. This is a real limit on what the audit trail can promise to cover. [`specs/application/product/tenant-administration/audit-log-visibility.md § Audit Log Visibility`](/specs/application/product/tenant-administration/audit-log-visibility.md#audit-log-visibility) states it as a boundary on that same promise, instead of leaving it implicit here alone. Scoping whatever credential a business unit grants there to what a specific issue's triage needs, instead of a standing account, is the business unit's own responsibility. PriceHorizon has no way to verify or enforce that scoping, since the grant happens entirely outside it, in the same way that PriceHorizon has no visibility into the access itself. Where the output goes to the fallback viewer, access runs through Platform admin's own governed access path, by federated claim or break-glass credentials ([`specs/application/technical/identity-and-access.md § Platform admin access`](/specs/application/technical/identity-and-access.md#platform-admin-access)). That is the same path that authenticates every other Platform admin activity, and it generates its own Audit Log Entry ([`specs/application/technical/data-model.md § Core Data Model § Audit Log § Audit Log Entry`](/specs/application/technical/data-model.md#audit-log-entry)) the moment it is used. It is not a second, separately managed credential for observability.

The application's metrics carry no business content by construction: request counts, latency percentiles, and the retry and failure rates behind its failure states, [`§ Engineering and Production Considerations § Orchestration § Question run [States.State: predict_failed]`](#question-run), [`§ Engineering and Production Considerations § Orchestration § Question run [States.State: position_failed]`](#question-run), and [`§ Engineering and Production Considerations § Orchestration § Question run [States.State: simulate_failed]`](#question-run). Traces, logs, and these metrics alike are retained on an operational cadence of weeks, not years. That is long enough to debug a recently reported issue. They are not a compliance record.

Every log entry is written at one of the standard levels, the same severity scale OpenTelemetry's logging data model uses. In decreasing order of verbosity, they are trace (every step, the most detail, suited to active debugging), debug, info (the default for normal operation), and error (only genuine failures). Control over the threshold is asymmetric, not shared equally. It matches where the rest of this architecture already draws the line between a business-unit fact and the underlying mechanism ([`specs/application/product/tenant-administration/application-log-control.md`](/specs/application/product/tenant-administration/application-log-control.md)). [`specs/application/technical/control-plane-service/control-plane.md § Control Plane § Configuration change path`](/specs/application/technical/control-plane-service/control-plane.md#configuration-change-path) sets who may change which threshold. A Control plane admin lowers their own business unit's threshold toward trace when they want Acme AI to have more detail to resolve an issue they are experiencing, without needing to ask first. That is the same self-service philosophy already behind triggering an out-of-cycle materialization run. A Platform admin's installation-wide default and override serve deeper, cross-cutting debugging. The mechanism itself stays with Acme AI, for the same reason the archetype rules and weighting rubrics do.

The mechanism is traces and spans, not just discrete log events. Each state in the Question run State Machine ([`§ Engineering and Production Considerations § Orchestration § Question run`](#question-run)) is its own span, from the initial state through to the terminal state a run ends in. A full run is one trace. The trace gives a request's path and per-step timing through the pipeline, not just a list of events about it.

Each span carries the standard OpenTelemetry resource attributes identifying the infrastructure it ran on: host, container, or pod, whichever unit the client's own infrastructure team already monitors. With them, a slow or failed trace can be correlated against that infrastructure's performance at the same moment. Acme AI never collects or operates that infrastructure monitoring itself, the same boundary this section draws. Every span also carries the application_version that ran it. A span whose state invokes a versioned model carries that model's registry version too ([`specs/application/technical/model-registry.md § Model registry`](/specs/application/technical/model-registry.md#model-registry)). The versioned models are those behind forecast computation, driver attribution, the positioning archetype rule, simulation, embedding and extraction. These are the same versions already pinned on a persisted Effective Price Forecast row or captured directly for Position and Simulate, now attached to the trace that produced them as well. So a behavior change noticed months later in a debugging session can be pinned to the exact release or model version responsible, not inferred from when the report happened to arrive. Nothing beyond that correlation is assembled for a joint look. The client's own infrastructure team, or Acme AI engineering during a joint support session, reads the trace wherever it was forwarded.

The same tracing discipline extends to the materialization service's batch path. [`§ Engineering and Production Considerations § Orchestration`](#orchestration) describes the batch path as the other half of the orchestration engine, sharing "one set of retry, failure-handling, and scheduling semantics" with the live path. The batch path covers separate processes, not one, since they run on different cadences and neither is nested inside the other. Grid materialization gets one trace per business unit's materialization run. That matches the existing rule that at most one materialization run is in flight per business unit at a time ([`specs/application/technical/materialization-service/forecast-materialization.md § Forecast materialization`](/specs/application/technical/materialization-service/forecast-materialization.md#forecast-materialization)). Each grid cell, one competitor, brand, geography, and horizon combination, gets its own child span, and the cells are computed in parallel. Each named step within a cell's computation gets its own span in turn: product matching, geography normalization, currency normalization, and forecast computation. The spans use the same named Algorithms and sections that [`specs/application/technical/materialization-service/reconciliation.md § Product and Geography Reconciliation`](/specs/application/technical/materialization-service/reconciliation.md#product-and-geography-reconciliation) already defines, not a second, separately maintained process description invented for tracing's sake. So a specific Effective Price Forecast row's data_vintage_id can be traced back to more than the inputs it used, which the Rationale Record already covers. It can be traced to how the computation that produced it ran: which step took how long, and whether anything retried. That is the same infrastructure-correlation benefit as the live path, applied to where a business user's forecast came from.

Document vectorization is a separate process, with its own trace per ingested document (or per corpus-refresh batch). The trace is independent of any specific grid cell, because a Driver Signal the process produces may feed many future cells' computations, or sit unused for months. The process follows the cadence of [`specs/application/technical/materialization-service/driver-signal-extraction.md § Vector and semantic mapping, with structured extraction`](/specs/application/technical/materialization-service/driver-signal-extraction.md#vector-and-semantic-mapping-with-structured-extraction), "the same cadence as the corpus refresh," not tied to a business unit's grid materialization run. That section reads every document first. It names distinct operations on each document that states an event in a driver category: the document is chunked, embedded, and extracted. These operations are separate spans, not one. Embedding and extraction are each their own model call. The registry ([`specs/application/technical/model-registry.md § Model registry`](/specs/application/technical/model-registry.md#model-registry)) names extraction as one of its LLM-based tools, a different model entirely from the one that embeds. So a slow or failed document is traceable to the operation responsible, whether chunking, the embedding call, or the extraction call, not just to "driver signal extraction" generically.

#### Comparing two delivered answers

Follow each question_asked entry to its Delivered Answer and referenced Effective Price Forecast ([`specs/application/technical/data-model.md § Core Data Model § Pipeline and Answer Artifacts § Delivered Answer`](/specs/application/technical/data-model.md#delivered-answer)). Compare the inputs to each figure as delivered. Predict uses the forecast’s business unit, competitor, brand, geography, horizon, data vintage, application version, numeric model versions and business-unit configuration version. An allocated Predict figure also uses the requested geography, grounded parent, allocation source version and weight. Position inherits those forecast inputs and adds its resolved matches, decision type, origin prices and delivery-time data, configuration, application and numeric model versions. Simulate inherits the inputs of the positioning options it uses and adds its own effective inputs and versions. A reused forecast carries its original pins through every dependent layer. A configuration_changed entry can identify an intervening edit.

For each requested layer compare its recorded availability. For comparable, available layers compare the delivered forecast, confidence scorecard and numeric rationale, positioning seeds, prices, groups and every delivered numeric output and confidence figure. Simulate covers projected share, volume, category growth, revenue, margin and simulation confidence ([`specs/application/product/answer-engine/simulate.md § Simulate: what follows for the business`](/specs/application/product/answer-engine/simulate.md#simulate-what-follows-for-the-business)). Match options by business identity and seed membership within the request. Compare the delivered groups and their numeric contents independently of delivery-local IDs and explanatory wording.

**Construct:** `specs/methodology/modeling-constructs.md § Constructs § Decision Table` \
**Conditions:** Known input difference?, Input evidence complete?, Availability known?, Same availability?, Stage available?, Known field difference?, Evidence complete?

| Known input difference? | Input evidence complete? | Availability known? | Same availability? | Stage available? | Known field difference? | Evidence complete? | Layer verdict |
|---|---|---|---|---|---|---|---|
| true | - | - | - | - | - | - | Changed inputs |
| false | false | - | - | - | - | - | Insufficient evidence |
| false | true | false | - | - | - | - | Insufficient evidence |
| false | true | true | false | - | - | - | Different availability |
| false | true | true | true | false | - | - | Unavailable in both |
| false | true | true | true | true | true | - | Different figures |
| false | true | true | true | true | false | false | Insufficient evidence |
| false | true | true | true | true | false | true | Equal figures |

Report any established input difference alongside each missing input. When no input difference is established, a comparison can proceed only with evidence for all inputs used by the layer. For available layers, a known field difference includes a changed figure, a changed option or group membership, or a field delivered on only one side. An explicitly unavailable figure differs from zero. A field missing from an older record leaves a gap in the evidence. Report each established difference by layer and field alongside any such gaps. Continue with every other requested layer. A delivery-wide numeric match requires matching availability for all requested layers and equal figures for every available layer.

#### Release activation

The client elects the release and its operator outside PriceHorizon. Its infrastructure administration binds an installation-unique activation attempt to the exact elected package, the authorized deployment principal and the expected active revision. An Acme AI-managed attempt authenticates the named Platform admin and requires current installation support permission at activation. A self-managed attempt authenticates the client infrastructure principal locally. Both use the same installation-side activation path.

The authenticated principal must match the attempt's immutable operator and package binding before it can obtain a result. A managed operator must also hold current support permission. Staging makes all elected service and model artifacts ready before publication. The installation locks the activation record and takes the first matching disposition. A terminal outcome remains retrievable by the authorized operator across restart and audit retention. An uncertain commit is unresolved until the durable attempt record can establish its outcome.

**Construct:** `specs/methodology/modeling-constructs.md § Constructs § Decision Table` \
**Hit Policy:** First \
**Conditions:** Authorized binding?, Attempt outcome, Expected active revision matches?, All artifacts ready?, Publication transaction available?

| Authorized binding? | Attempt outcome | Expected active revision matches? | All artifacts ready? | Publication transaction available? | Disposition |
|---|---|---|---|---|---|
| false | - | - | - | - | Deny access to the attempt |
| true | "success", "failure" | - | - | - | Return the recorded outcome |
| true | unresolved | - | - | - | Wait for the durable outcome before retrying |
| true | open | false | - | - | Record a terminal failure after confirming the attempt did not publish |
| true | open | true | false | - | Keep the active revision and resume staging |
| true | open | true | true | false | Keep the active revision and retry the same attempt |
| true | open | true | true | true | Publish the elected release |

Publication rechecks the binding, expected active revision and artifact readiness within one installation database transaction. It serializes competing activations and effective pin changes. The transaction publishes the active revision, records terminal success for the attempt and writes one installation-wide upgrade entry with the application version and all effective model pins, including provider and dated version for external calls. Each model-only release retains the active application version and has its own entry. Services serve work only from a committed revision. The client’s external routing configuration remains under its own infrastructure administration.

A confirmed terminal failure records the attempt outcome and failed upgrade together, without resulting versions. If that transaction is unavailable, the attempt remains unresolved until its outcome can be recorded. A fresh authorized attempt can retry a terminal failure. The client can read either operator's completed activation in its installation-wide audit history.

#### Audit log purge

The nightly materialization schedule starts the purge ([`specs/application/technical/materialization-service/forecast-materialization.md § Forecast materialization`](/specs/application/technical/materialization-service/forecast-materialization.md#forecast-materialization)). Each run retains its identity and its UTC start time across interruptions. The scan reads candidate IDs for that run in ascending order. Each deletion and the completion record serialize with retention changes. Readers obtain the installation’s greatest applied cutoff and the retained entries from the same committed snapshot. A raise protects records still present at its commit. It cannot restore an earlier deletion or move the coverage boundary backward.

**Construct:** `specs/methodology/modeling-constructs.md § Constructs § Algorithm` \
**Inputs:**
  - run identity
  - candidate ids

**Output:** none \
**Runs When:**
  - the nightly materialization schedule requests an audit purge. A missed run starts when service resumes. A delayed run starts once. A crash, conflicting transaction or uncertain commit resumes the same run from step 1 after uncommitted work rolls back.

| Step | Action |
|---|---|
| 1 | Create or reopen the durable run under its identity, preserving the original UTC start time and candidate scan on retry |
| 2 | If purge completed(run identity), End; otherwise, continue |
| 3 | For each candidate of candidate ids, by candidate ascending: steps 4 to 9 |
| 4 | Open a deletion transaction serialized with retention changes and concurrent processing of this candidate |
| 5 | Set observed to purge observation(run identity, candidate) |
| 6 | Run [`§ Engineering and Production Considerations § Security and governance § Audit log purge § Entry disposition`](#entry-disposition) with Entry still present? as observed.present, with Entry exempt? as observed.exempt, with Before effective cutoff? as observed.older, giving Disposition |
| 7 | If Disposition = "Delete", remove the audit entry and its associated Delivered Answer if present; otherwise, continue |
| 8 | If Disposition = "Delete", advance the run and installation cutoff records to at least the observed cutoff; otherwise, continue |
| 9 | Commit the candidate transaction |
| 10 | Begin a completion transaction serialized with retention changes and other completions for this run |
| 11 | If purge completed(run identity), close the transaction, End; otherwise, continue |
| 12 | Set final cutoff to purge completion cutoff(run identity) |
| 13 | Record one retention_purge event with the run identity and final cutoff, advance the installation boundary to at least that cutoff, and mark the run complete in the same commit |
| 14 | End |

##### Entry disposition

The comparison uses the candidate’s occurred_at. The exemption covers every retention_purge event and the installation’s latest recorded frontier_models_changed event. A later routing entry supersedes that exemption ([`specs/application/technical/control-plane-service/control-plane.md § Control Plane § External model routing changes`](/specs/application/technical/control-plane-service/control-plane.md#external-model-routing-changes)). Removing a Delivered Answer leaves its referenced forecast under the forecast’s own lifecycle.

**Construct:** `specs/methodology/modeling-constructs.md § Constructs § Decision Table` \
**Conditions:** Entry still present?, Entry exempt?, Before effective cutoff?

| Entry still present? | Entry exempt? | Before effective cutoff? | Disposition |
|---|---|---|---|
| false | - | - | Already removed |
| true | true | - | Keep |
| true | false | false | Keep |
| true | false | true | Delete |

## Facts

**Records:**
  - **Name:** is the failed response ready? \
    **Type:** boolean \
    **Means:** a terminal forecast, positioning or simulation failure has fixed the response to this question

  - **Name:** completed stage artifacts \
    **Type:** list<context> \
    **Means:** ordered stage identities and immutable result references that completed for the current question before the failure, empty when Predict failed

  - **Name:** returned stage artifacts \
    **Type:** list<context> \
    **Means:** ordered stage identities and immutable result references actually included in the failed or partial response

  - **Name:** purge completed \
    **Type:** function<string> -> boolean \
    **Means:** the durable completion marker for the supplied run identity, read in the current transaction

  - **Name:** purge observation \
    **Type:** function<string, number> -> context<present: boolean, exempt: boolean, older: boolean, cutoff: date and time> \
    **Means:** the installation database’s observation of the run and candidate under the deletion transaction. The cutoff is the run’s fixed UTC start time minus the current committed retention_period. Present records existence, exempt records the applicable exemption, and older means the present entry’s occurred_at is strictly earlier than the cutoff. Both tests are false for an absent entry.

  - **Name:** purge completion cutoff \
    **Type:** function<string> -> date and time \
    **Means:** the database reads the run’s greatest cutoff committed with an actual deletion. For a run with no deletions, it uses the original UTC run time minus the retention_period read in the completion transaction.

  - **Name:** forecast lookup \
    **Type:** string \
    **Values:** "stored", "live required", "unavailable" \
    **Means:** the resolved retrieval route. A publication or coverage unavailable result carries its reason to the response. Allocation requests resolve the grounded parent before selecting its bundle.

  - **Name:** business unit resolution \
    **Type:** string \
    **Values:** "denied", "unsettled", "resolved" \
    **Means:** whether access was denied, a business unit still needs clarification or a granted unit has been selected

  - **Name:** entity resolution \
    **Type:** string \
    **Values:** "unresolved", "resolved" \
    **Means:** whether the question’s entities resolve uniquely within the selected business unit

  - **Name:** decision type resolution \
    **Type:** string \
    **Values:** "unsettled", "settled" \
    **Means:** whether the question's decision type has been settled

## Open Questions

**Records:**
  - **Name:** Retry Policy \
    **Open Question:** How many times is a failed step retried, and on what backoff, before the step counts as failed? \
    **Provisional Answer:** On the live path, a failed step is retried up to twice, waiting 200 and then 400 milliseconds, so a failing step's waits add no more than 600 milliseconds to its latency budget. On the batch path, it is retried up to three times, waiting one, two and then four minutes. Both follow the one set of retry semantics the orchestration engine gives both paths, differing only in these values. \
    **Impacts:** the Question run State Machine's failure states, [`§ Engineering and Production Considerations § Orchestration § Question run [States.State: predict_failed]`](#question-run), [`§ Engineering and Production Considerations § Orchestration § Question run [States.State: position_failed]`](#question-run) and [`§ Engineering and Production Considerations § Orchestration § Question run [States.State: simulate_failed]`](#question-run), which it fixes once a step's retries are exhausted, and the one set of retry semantics both paths share ([`§ Engineering and Production Considerations § Orchestration`](#orchestration)); the live path's response time in the low seconds ([`§ Engineering and Production Considerations`](#engineering-and-production-considerations)); and when an answer degrades after exhausting its retries ([`specs/application/product/trust-and-explainability/degraded-answer-behavior.md § Degraded Answer Behavior`](/specs/application/product/trust-and-explainability/degraded-answer-behavior.md#degraded-answer-behavior)).

  - **Name:** Retention Decrease \
    **Open Question:** How is a genuine decrease to an installation's retention period made, and is it contract- and legal-reviewed? \
    **Provisional Answer:** It is not made: the retention period only rises, through the control plane, and nothing shortens it. \
    **Impacts:** the deletion boundary in [`§ Engineering and Production Considerations § Security and governance § Audit log purge`](#audit-log-purge) and the raise-only setting in [`specs/application/technical/control-plane-service/control-plane.md § Control Plane § Configuration change path`](/specs/application/technical/control-plane-service/control-plane.md#configuration-change-path).
