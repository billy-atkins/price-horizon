## Engineering and Production Considerations

**Data pipeline cadence.** Syndicated and POS data are ingested in batch on a daily or weekly cycle. Price-change signals that matter for a fast-moving competitive response are ingested in near real time. The qualitative corpus is re-embedded on a periodic cycle as new documents arrive. The forecast materialization job ([`specs/application/technical/materialization-service/forecast-materialization.md § Forecast materialization`](/specs/application/technical/materialization-service/forecast-materialization.md#forecast-materialization)) runs immediately after each competitor data refresh, one of the triggers that section names, so the materialized grid is never more stale than its source.

**Latency and cost budget.** The scorecard and narrative layers need a response time in the low seconds to feel like a search box. The drill-down and full decomposition can tolerate more, since the user has already committed to exploring. Caching common question intents keeps the frequent questions fast and cheap. It does not weaken the guarantee that an uncached query still runs the full pipeline.

**API shape.** A single REST API serves both the answer surface and the control plane, with one auth model and one set of client libraries for both. The service boundary ([`§ Engineering and Production Considerations § Service boundaries`](#service-boundaries)) separates the two, not the API surface. [`specs/application/technical/query-service/intent-and-retrieval.md § Dynamic Retrieval and Weighting (when the question is asked) § Session context`](/specs/application/technical/query-service/intent-and-retrieval.md#session-context) states what a question request carries and what every answer returns about its business unit and kind of decision. JSON:API-style query conventions keep the answer surface from over-fetching a deeply nested response. `include=` pulls in related resources in one round trip, with dotted paths reaching into nested Positioning Candidates when needed (`include=positions.rationale,positions.simulatedOutcome`). `fields[type]=` sparse fieldsets avoid pulling a full Rationale Record when a caller needs only a few fields. The performance work happens in the data layer, not the API. The Effective Price Forecast already bundles the fact and its rationale into one read, so an include or a field selection serves already-joined data, not a chain of separate lookups.

**Deployment and versioning.** [`specs/application/product/platform-and-compliance-operations/deployment-topology.md`](/specs/application/product/platform-and-compliance-operations/deployment-topology.md) states the deployment topology and its per-business-unit configuration scoping. The business-unit-scoped rows of [`specs/application/technical/control-plane-service/control-plane.md § Control Plane`](/specs/application/technical/control-plane-service/control-plane.md#control-plane)'s Decision Table are the technical-specific configuration surface underneath that same scoping. The mechanism itself stays canonical across every installation: the seeding and consolidation logic, and the reconciliation approach. Only its tuning is configuration.

The application and the models version independently of each other. The application version covers the orchestration, the positioning engine's logic, the reconciliation mechanism, the Event Type Taxonomy ([`specs/application/technical/data-model.md § Core Data Model § Pipeline and Answer Artifacts § Signal Routing Rule`](/specs/application/technical/data-model.md#signal-routing-rule)), the horizon set the grid materializes against, the connector built for each data source type, and the API and UI contracts. Each model and weighting rubric in the registry ([`specs/application/technical/model-registry.md § Model registry`](/specs/application/technical/model-registry.md#model-registry)) versions on its own cadence, and is validated independently against the golden-question harness ([`specs/application/technical/evaluation-and-monitoring.md § Evaluation and monitoring`](/specs/application/technical/evaluation-and-monitoring.md#evaluation-and-monitoring)). A customer can take an application upgrade without any model changing underneath them. A customer can also receive a recalibrated model without an application upgrade forcing new UI or workflow changes on them at the same time. Acme AI ships each as its own release. A customer's installation pins to a specific application version and a specific version of every model it calls. The installation is upgraded Acme AI-managed or self-managed, as [`specs/application/product/platform-and-compliance-operations/versioned-upgrades.md § Versioned Upgrades`](/specs/application/product/platform-and-compliance-operations/versioned-upgrades.md#versioned-upgrades) describes.

### Orchestration

Once a question is asked, the live-path pipeline needs a workflow layer built for retries, partial failure, and observability, not a single long prompt. Each step in it is independently testable. The pipeline is a fixed, deterministic sequence with parallel fan-out and fan-in, not a graph where a model decides the next step. So the right category of tool is a durable execution engine built for retryable pipelines, not an agent framework. [`specs/application/technical/stack.md § Technical Stack`](/specs/application/technical/stack.md#technical-stack) names the engine. The engine runs both the query service's live path and the materialization service's batch path. The batch path runs on the cadence [`specs/application/technical/materialization-service/forecast-materialization.md § Forecast materialization`](/specs/application/technical/materialization-service/forecast-materialization.md#forecast-materialization) sets, and its runs start without any question being asked. Running both paths on the same orchestration engine is part of what keeps a live answer and a materialized one from ever disagreeing ([`specs/application/technical/materialization-service/forecast-materialization.md § Forecast materialization`](/specs/application/technical/materialization-service/forecast-materialization.md#forecast-materialization)). The two paths share one set of retry, failure-handling, and scheduling semantics, not separate tools whose behavior has to be kept in sync with each other.

### Service boundaries

The system runs as separate services, not one. A different property justifies each service, and none is split for its own sake. The query service runs the live path ([`specs/application/technical/query-service/intent-and-retrieval.md § Dynamic Retrieval and Weighting (when the question is asked)`](/specs/application/technical/query-service/intent-and-retrieval.md#dynamic-retrieval-and-weighting-when-the-question-is-asked), [`specs/application/technical/predict-computation.md § Predict Computation`](/specs/application/technical/predict-computation.md#predict-computation), and [`specs/application/technical/query-service/layered-output-synthesis.md § Layered Output Synthesis (producing the answer)`](/specs/application/technical/query-service/layered-output-synthesis.md#layered-output-synthesis-producing-the-answer)). It is request-driven and held to the latency budget. The materialization service runs the batch path: forecast materialization, driver signal extraction, and product and geography reconciliation. It is throughput-oriented and tolerant of long-running jobs, with nothing in common operationally with an interactive request. The control plane service is separated for a security reason, not a workload reason. Every operation on it writes configuration that governs every future answer: reference data, materiality thresholds, the IdP claim mapping itself. That makes it a categorically more sensitive surface than the query service's read-only path. Only the control plane service holds write credentials to the reference tables in [`specs/application/technical/data-model.md § Core Data Model § Reference and Master Data`](/specs/application/technical/data-model.md#reference-and-master-data). The query service never does. So a vulnerability in the far larger, far more exposed query surface cannot reach the capability to change what a competitor's code means or what a business unit's threshold is. This is the mechanism behind the architectural separation [`specs/application/product/identity-and-access/using-and-administering-kept-apart.md § Using and Administering Kept Apart`](/specs/application/product/identity-and-access/using-and-administering-kept-apart.md#using-and-administering-kept-apart) states.

[`specs/application/technical/architecture.md § Architecture Overview § Diagrams § Layer Composition`](/specs/application/technical/architecture.md#layer-composition) and [`specs/application/technical/architecture.md § Architecture Overview § Diagrams § Trust Boundaries`](/specs/application/technical/architecture.md#trust-boundaries) render this.

### Security and governance

The primary control is deployment topology. Each customer's data stays inside the customer's own environment by construction. There is no shared store for it to leak through, save what the client lets a frontier model provider see ([`specs/application/technical/model-registry.md § Model registry`](/specs/application/technical/model-registry.md#model-registry)). Acme AI's access as the operator is a secondary, governed layer of access control and audit logging. It is not a substitute for the residency decision itself.

Within that environment, IdP-asserted claims ([`specs/application/technical/identity-and-access.md § Business unit access, federated`](/specs/application/technical/identity-and-access.md#business-unit-access-federated)) are the enforcement boundary. Different services and different stores check them differently. In the vector database, the claims are checked by the per-namespace credentials [`specs/application/technical/secrets-management.md § Secrets management`](/specs/application/technical/secrets-management.md#secrets-management) issues the query service, over the namespaces [`specs/application/technical/data-model.md § Core Data Model § Harmonized quantitative foundation`](/specs/application/technical/data-model.md#harmonized-quantitative-foundation) partitions the vector database into. In the structured database and the materialized grid, they are checked by the claim filter that [`specs/application/technical/query-service/intent-and-retrieval.md § Dynamic Retrieval and Weighting (when the question is asked) § Intent parsing and decoupling`](/specs/application/technical/query-service/intent-and-retrieval.md#intent-parsing-and-decoupling) applies on every retrieval. At the control plane service, they are checked by the Control plane admin claim check [`specs/application/technical/identity-and-access.md § Business unit access, federated`](/specs/application/technical/identity-and-access.md#business-unit-access-federated) describes, behind the write credentials [`§ Engineering and Production Considerations § Service boundaries`](#service-boundaries) confines to that service. Platform admin access, Acme AI's own, follows [`specs/application/technical/identity-and-access.md § Platform admin access`](/specs/application/technical/identity-and-access.md#platform-admin-access). Its break-glass credentials are held in the vault [`specs/application/technical/secrets-management.md § Secrets management`](/specs/application/technical/secrets-management.md#secrets-management) describes.

Competitor pricing intelligence and licensed syndicated data both carry real contractual and competitive sensitivity on top of that. Access control needs to reflect data licensing terms. Every generated answer needs an audit trail sufficient to defend it internally or to a retailer. [`specs/application/technical/architecture.md § Architecture Overview § Diagrams § Trust Boundaries`](/specs/application/technical/architecture.md#trust-boundaries) renders this.

An Audit Log Entry ([`specs/application/technical/data-model.md § Core Data Model § Audit Log § Audit Log Entry`](/specs/application/technical/data-model.md#audit-log-entry)) is application data, not a log in the observability sense. It never touches the observability pipeline that application logs flow through (this section's application logging passage).

A middleware component writes the entry. The pattern is the same by whichever name a given stack calls it: ASP.NET Core-style middleware or an Action Filter, or a Servlet Filter or Spring's HandlerInterceptor in a JVM stack. The middleware wraps every request in the same pipeline, whichever of these it is:

- a Query user's question, arriving through the UI or a direct API call
- a Control plane admin's or an Identity admin's change through the control plane service
- a Platform admin action against the query, materialization, or control plane service ([`§ Engineering and Production Considerations § Service boundaries`](#service-boundaries))

So no individual action's business logic needs to know it is being audited.

Onboarding and upgrade are an exception to "every request". Neither runs through the request pipeline of any of those services. So Acme AI's internal provisioning and release tooling writes their audit entries directly, in place of the per-request middleware described here. Each entry joins that tooling's own transaction in the same disciplined way. Two entries record the installation's own activity instead of any request. The purge run that this section's retention steps describe writes a retention_purge entry. The control plane service writes a frontier_models_changed entry as the installation starts ([`specs/application/technical/model-registry.md § Model registry`](/specs/application/technical/model-registry.md#model-registry)).

The middleware buffers the auditable fact in memory as the request is handled. It flushes the fact immediately before the response is returned, not fire-and-forget afterward. Not every audited action writes anything of its own to flush alongside the fact. A diagnostic support session, viewing application logs, or reading the installation's pinned versions is read-only for Platform admin, with nothing else to join. A Query user's question is never read-only, whatever its path. The query service always persists a Delivered Answer ([`specs/application/technical/data-model.md § Core Data Model § Pipeline and Answer Artifacts § Delivered Answer`](/specs/application/technical/data-model.md#delivered-answer)) as the final step of producing any answer that reaches Predict. It does so whether that question's Predict stage was a grid lookup, per [`specs/application/technical/materialization-service/forecast-materialization.md § Forecast materialization`](/specs/application/technical/materialization-service/forecast-materialization.md#forecast-materialization), or a live computation, so the flush always has at least that Delivered Answer write to join, on top of the audit write itself.

An action may write something beyond its own Delivered Answer: onboarding, an upgrade, a configuration_changed edit against any of the self-service surfaces that [`specs/application/technical/control-plane-service/control-plane.md § Control Plane`](/specs/application/technical/control-plane-service/control-plane.md#control-plane)'s Decision Table names, or a question answered by a live computation that also persists an Effective Price Forecast row. There, the audit entry joins the same database transaction as whichever of those writes applies. If the transaction fails to commit for any reason, the audit write included, the whole request rolls back together. An action and its own audit entry are never separated.

Some of a business unit's settings shape an answer: its dead-zone threshold, a materiality threshold, an archetype's display label, or the display name of one of its competitors, of one of its geographies or of the business unit itself. A configuration_changed entry against one of these settings is, on committing, what increments that business unit's `business_unit_configuration_version`. Every Effective Price Forecast row pins itself to that same version. Any other configuration_changed entry, among them one against a data source's credentials, a log threshold, a glossary alias or an IdP claim mapping, is audited the same way but raises no version ([`specs/application/technical/data-model.md § Core Data Model § Pipeline and Answer Artifacts § Answer Provenance`](/specs/application/technical/data-model.md#answer-provenance)). So every version bump is one specific, attributable audit entry, recording who changed what, from what value, to what value, and when. It is not just a number that changed.

Where the action is read-only, such as a diagnostic session, viewing application logs, or reading the pinned versions, the audit write is the only write in the request. It runs in its own transaction, and the response is gated on that write's success. A Query user's question served straight from the grid is never this case. Its Delivered Answer and its audit entry are a pair in one transaction, and they gate the response together, under the same guarantee.

If the audit write itself fails, the request fails outright, as any other failure to complete an answer already does ([`specs/application/product/trust-and-explainability/degraded-answer-behavior.md § Degraded Answer Behavior`](/specs/application/product/trust-and-explainability/degraded-answer-behavior.md#degraded-answer-behavior)). No forecast is shown. What is shown is that one could not be computed, and the Query user is told to try again. An answer is never shown with no audit trail behind it, and a stale or partial substitute is never offered in its place. Either way, an action can never be left recorded as having happened, or its results shown, with no audit trail behind it. Nor can an audit entry be left behind for a write that itself rolled back.

Holding the audit record as application data is a design choice. An audit record needs long retention, a stable and versioned schema, transactional certainty, and to stay queryable through the Control Plane's self-service surface. No general telemetry backend is built to provide these, whether OpenTelemetry-native or a client's own observability platform. Nor is the audit record ever held in a shared, Acme-AI-hosted store spanning multiple customers, by the same residency principle this section states.

The audit record is retained for at least one year by default. That year is a floor, and the installation-wide retention_period setting can be raised above it to meet a client's contractual requirement. A raise is recorded the same way as any other governed configuration_changed entry, and governed as [`specs/application/technical/control-plane-service/control-plane.md § Control Plane`](/specs/application/technical/control-plane-service/control-plane.md#control-plane) sets out. A genuine decrease is outside self-service and outside routine governed configuration entirely ([`§ Open Questions [Name: Retention Decrease]`](#open-questions)).

Both the client and Acme AI can read the audit record, but not through the same surface, and not everyone reads the same slice of the table. A Control plane admin views every entry scoped to their own business unit through the self-service Control Plane surface. That takes in Acme AI's own access to the business unit, every configuration_changed edit made within it whichever admin made it, and their own Query users' questions alike. Through the same surface, the Control plane admin also views an installation-wide entry, such as a Platform admin's upgrade or an Identity admin's change to who holds the Platform admin role. An Identity admin views every IdP claim mapping change across the installation, and every question denied because its asker's access held no business unit. The Identity admin views them through the same surface every other business-unit activity already goes through ([`specs/application/product/tenant-administration/audit-log-visibility.md`](/specs/application/product/tenant-administration/audit-log-visibility.md)). This is the mechanism behind that section's promise that the audit record is one a client can see, not one it must trust happens somewhere out of sight. Acme AI views its own access, every configuration_changed edit, and every business unit's Query user activity across the installation. It views them through its own internal engineering tooling, not through any PriceHorizon product screen. Platform admin's other activities, onboarding, upgrades and diagnostic access, already work outside the client-facing product entirely in the same way.

The purge of what has aged past retention_period runs on the nightly schedule that materialization already keeps ([`specs/application/technical/materialization-service/forecast-materialization.md § Forecast materialization`](/specs/application/technical/materialization-service/forecast-materialization.md#forecast-materialization)). It reuses that schedule instead of adding a second rhythm for the system to run on. It runs as an Algorithm:

**Construct:** `specs/methodology/modeling-constructs.md § Constructs § Algorithm`

**Inputs:** the installation's Audit Log Entries, and its current retention_period

**Output:** every Audit Log Entry aged past retention_period deleted, with the Delivered Answer each references, but for the retention_purge entries and the latest frontier_models_changed entry, which are kept; and a retention_purge entry recording the run

| Step | Action |
|---|---|
| 1 | If an Audit Log Entry is left that this run has not checked, continue; otherwise, Go to step 7 |
| 2 | Take the next Audit Log Entry this run has not checked |
| 3 | If its action_type is retention_purge, or it is the latest frontier_models_changed entry, Go to step 6; otherwise, continue |
| 4 | If its occurred_at is older than the installation's current retention_period, continue; otherwise, the entry being checked again on a later run, Go to step 6 |
| 5 | Delete the entry, a hard delete, not an archive, since retaining compliance data longer than a stated purpose requires is its own exposure, not a safety margin, and, where it has a delivered_answer_id, that Delivered Answer row in the same operation, since nothing else in the system ever references it once its own audit entry is gone |
| 6 | If an Audit Log Entry is left that this run has not checked, Go to step 2; otherwise, continue |
| 7 | Record that this run happened as its own retention_purge entry, whether or not any entry qualified for deletion that night. End |

Step 3 excludes a retention_purge entry, the run's own record of itself, from deletion regardless of age. That entry is what proves the process has been running compliantly over time. The reason to keep it never diminishes the way an old access record's relevance does. Its volume is one entry per run, never one per business action, which makes it an exception worth making and not a loophole worth closing. The latest frontier_models_changed entry is kept for a reason of the same kind. It records which kinds of model call the installation now lets reach a frontier model provider, and the next change is recorded against it ([`specs/application/technical/model-registry.md § Model registry`](/specs/application/technical/model-registry.md#model-registry)), so it is never deleted while it is the latest. Once a later entry replaces it and its age passes the retention period, it is deleted as any other entry is.

The retention_period setting can only be raised through this design ([`specs/application/technical/control-plane-service/control-plane.md § Control Plane`](/specs/application/technical/control-plane-service/control-plane.md#control-plane), [`§ Open Questions [Name: Retention Decrease]`](#open-questions)). So the "current retention_period" that step 4 checks against is always the longest that has ever applied. Step 4 compares every entry against today's setting, not against whatever setting happened to be in effect the day the entry was written. That comparison never retroactively shortens a commitment already made. A raise takes effect immediately, and protects entries that would otherwise have aged out under the old, shorter setting. That is the outcome a client extending their own retention requirement expects.

Further capabilities follow directly from fields already on the Audit Log Entry, not from any new mechanism. They exist so the audit trail can be used under pressure, not only consulted after the fact.

Verifying the repeatability guarantee ([`specs/application/product/trust-and-explainability/guarantees.md § Guarantees This Answer Engine Makes`](/specs/application/product/trust-and-explainability/guarantees.md#guarantees-this-answer-engine-makes)) in production is a matter of comparing two question_asked entries for what looks like the same question, side by side. The comparison reads each entry's referenced Delivered Answer's Effective Price Forecast, and that forecast's pinned key: competitor, business unit, geography, horizon, data_vintage_id, application_version, model_versions, and business_unit_configuration_version ([`specs/application/technical/data-model.md § Core Data Model § Pipeline and Answer Artifacts § Effective Price Forecast`](/specs/application/technical/data-model.md#effective-price-forecast)). An identical key with a different forecast value is a defect worth escalating. An identical key with an identical forecast value confirms the guarantee held. A changed key explains a legitimate difference, instead of leaving it looking like an unexplained one: a data refresh landed in between, or a configuration_changed entry bumped the version in between. The configuration_changed entry is what makes that explanation traceable to a specific edit instead of an inference.

Investigating a non-technical executive's complaint about what they were told never depends on recomputing anything. The Delivered Answer record captures directly what Position and Simulate produced, and the exact application and model versions that produced it, alongside the forecast reference and the rendered narrative, so every piece of one delivered answer lives in one row, referenced as a whole by `delivered_answer_id`. A question_asked entry's `delivered_answer_id` points to the one record holding every piece together. Nothing about a past answer ever needs to be recomputed to know what it was.

A retained record measured in years is only as useful as someone's ability to find one entry inside it. That is a narrower problem than a general log search engine solves, because every field on the Audit Log Entry schema is already structured: a foreign key, an enum, a timestamp. No field is an unstructured line of text parsed and indexed after the fact. The filters are actor, action_type, and occurred_at as a bounded time range. For a question_asked entry, they include the competitor and geography named on its referenced Delivered Answer's Effective Price Forecast. For a configuration_changed entry, they include its changed_field. Each of these filters is therefore ordinary indexed-column filtering against the same structured database the audit table already lives in. It matches ranges and exact values already known, not a purpose-built search index bolted on top. The referenced Delivered Answer's `rendered_narrative` is the one free-text field, natural language by nature, and it is the only field keyword search runs against.

A filtered view defaults to a recent window of thirty days, not the full retention period. It shows a visible count of matching entries by day across that window. So a reviewer sees where activity clusters before reading a single row, instead of only after stumbling onto it. A cluster might be a spike in outcomes of [`§ Engineering and Production Considerations § Orchestration [States.State: query_denied]`](#orchestration), or several configuration_changed edits within the same hour. Bulk forecast review ([`specs/application/product/accuracy-governance.md § Tracking Forecast Accuracy`](/specs/application/product/accuracy-governance.md#tracking-forecast-accuracy)) shows a pattern across many forecasts at once, not one at a time, for the same reason.

Selecting an entry expands its full detail without losing the current filter. The detail holds the referenced Delivered Answer, with its positioning candidates, simulated outcomes, and rendered narrative together. It also holds a link into the evidence already exposed for its referenced forecast ([`specs/application/product/answer-engine/predict.md § Predict: what will the competitor do`](/specs/application/product/answer-engine/predict.md#predict-what-will-the-competitor-do)). That section's evidence drill-down already establishes the "without leaving the analysis" pattern. The audit detail extends the same pattern to an audit entry, instead of inventing one separately for it.

The filtered set can be exported to a flat file. The export holds exactly the rows matching, never a capped sample. A flat file is the form this record most often needs to take to leave the product. It is handed to an auditor, legal, or the client's own security team, none of whom need a PriceHorizon login of their own to receive it. The export never carries a referenced Delivered Answer's content, only the `delivered_answer_id` reference itself. The Delivered Answer record exists because it restates an answer's protected substance directly, not by reference. A flat file leaving the product entirely is the uncontrolled destination that substance is never allowed to reach anywhere else in this design. The Delivered Answer's content stays viewable in place, through the governed surfaces this section describes. An export never carries it.

Application logging ([`specs/application/product/logging-and-traceability.md § Logging and Traceability § Application Log`](/specs/application/product/logging-and-traceability.md#application-log)) is a concern distinct from the audit log. It serves debugging why a step failed, not tracking who accessed what. It covers the application only. The infrastructure PriceHorizon runs on, the servers, network, and storage, is the responsibility of the client's own infrastructure team. That team monitors it with whatever tooling it already runs in the client's environment, since PriceHorizon is self-hosted inside that environment, never Acme-AI-hosted ([`specs/application/product/platform-and-compliance-operations/deployment-topology.md`](/specs/application/product/platform-and-compliance-operations/deployment-topology.md)).

The application's OpenTelemetry signals, its traces, logs and metrics alike, never carry the categories of protected content: a forecast's quantitative values, a Driver Signal's document content, credential material, or a raw IdP claim payload. Every entry and trace does carry the Query user's identity, the same claim already resolved during intent parsing, so a specific executive's reported issue can be traced to its logs directly. Every entry and trace also carries the application_version that produced it. That version keeps changing over successive releases, and a log line without it cannot be placed against the release that behaved that way.

Application log content has no PriceHorizon product screen at all, for either role. A Control plane admin can raise the threshold that controls how much gets captured ([`specs/application/product/tenant-administration/application-log-control.md`](/specs/application/product/tenant-administration/application-log-control.md)), but never reads the resulting content. Reading it is not what the Control plane admin's self-service surface is for.

The application writes its structured log lines, spans and metrics to standard output or a log file. That is the ordinary mechanism for a self-hosted application, not a custom export path of its own. A standard forwarding agent deployed within the installation tails that output and forwards it to whatever observability platform the client already runs. Acme AI stands up no redundant tool inside an environment the client already instruments. This extends the same reasoning, that the client already has infrastructure tooling of its own, to the application layer. Where a client has no platform of their own, the same agent forwards instead to a self-hosted, OpenTelemetry-compatible viewer, shipped alongside PriceHorizon as the fallback default. Either way, PriceHorizon requires no connection outside the client's own environment. Where the client's own platform runs is the client's choice. PriceHorizon never sends any of this output to anything Acme AI hosts, and never combines it with another customer's.

How Acme AI engineering gets access to view the output differs by which path applies. So does what PriceHorizon's audit trail can see of that access. Where the output goes to the client's own platform, whatever the client grants there is the client's own process. That process is outside PriceHorizon's access model to define, and outside its Audit Log to observe. PriceHorizon has no visibility into an access that never touches it. This is a real limit on what the audit trail can promise to cover. [`specs/application/product/tenant-administration/audit-log-visibility.md § Audit Log Visibility`](/specs/application/product/tenant-administration/audit-log-visibility.md#audit-log-visibility) states it as a boundary on that same promise, instead of leaving it implicit here alone. Scoping whatever credential a business unit grants there to what a specific issue's triage needs, instead of a standing account, is the business unit's own responsibility. PriceHorizon has no way to verify or enforce that scoping, since the grant happens entirely outside it, in the same way that PriceHorizon has no visibility into the access itself. Where the output goes to the fallback viewer, access runs through Platform admin's own governed access path, by federated claim or break-glass credentials ([`specs/application/technical/identity-and-access.md § Platform admin access`](/specs/application/technical/identity-and-access.md#platform-admin-access)). That is the same path that authenticates every other Platform admin activity, and it generates its own Audit Log Entry ([`specs/application/technical/data-model.md § Core Data Model § Audit Log § Audit Log Entry`](/specs/application/technical/data-model.md#audit-log-entry)) the moment it is used. It is not a second, separately managed credential for observability.

The application's metrics carry no business content by construction: request counts, latency percentiles, and the retry and failure rates behind its failure states, [`§ Engineering and Production Considerations § Orchestration [States.State: predict_failed]`](#orchestration), [`§ Engineering and Production Considerations § Orchestration [States.State: position_failed]`](#orchestration), and [`§ Engineering and Production Considerations § Orchestration [States.State: simulate_failed]`](#orchestration). Traces, logs, and these metrics alike are retained on an operational cadence of weeks, not years. That is long enough to debug a recently reported issue. They are not a compliance record.

Every log entry is written at one of the standard levels, the same severity scale OpenTelemetry's logging data model uses. In decreasing order of verbosity, they are trace (every step, the most detail, suited to active debugging), debug, info (the default for normal operation), and error (only genuine failures). Control over the threshold is asymmetric, not shared equally. It matches where the rest of this architecture already draws the line between a business-unit fact and the underlying mechanism ([`specs/application/product/tenant-administration/application-log-control.md`](/specs/application/product/tenant-administration/application-log-control.md)). [`specs/application/technical/control-plane-service/control-plane.md § Control Plane`](/specs/application/technical/control-plane-service/control-plane.md#control-plane) sets who may change which threshold. A Control plane admin lowers their own business unit's threshold toward trace when they want Acme AI to have more detail to resolve an issue they are experiencing, without needing to ask first. That is the same self-service philosophy already behind triggering an out-of-cycle materialization run. A Platform admin's installation-wide default and override serve deeper, cross-cutting debugging. The mechanism itself stays with Acme AI, for the same reason the archetype rules and weighting rubrics do.

The mechanism is traces and spans, not just discrete log events. Each state in the Orchestration State Machine ([`§ Engineering and Production Considerations § Orchestration`](#orchestration)) is its own span, from the initial state through to the terminal state a run ends in. A full run is one trace. The trace gives a request's path and per-step timing through the pipeline, not just a list of events about it.

Each span carries the standard OpenTelemetry resource attributes identifying the infrastructure it ran on: host, container, or pod, whichever unit the client's own infrastructure team already monitors. With them, a slow or failed trace can be correlated against that infrastructure's performance at the same moment. Acme AI never collects or operates that infrastructure monitoring itself, the same boundary this section draws. Every span also carries the application_version that ran it. A span whose state invokes a versioned model carries that model's registry version too ([`specs/application/technical/model-registry.md § Model registry`](/specs/application/technical/model-registry.md#model-registry)). The versioned models are those behind forecast computation, driver attribution, the positioning archetype rule, simulation, embedding and extraction. These are the same versions already pinned on a persisted Effective Price Forecast row or captured directly for Position and Simulate, now attached to the trace that produced them as well. So a behavior change noticed months later in a debugging session can be pinned to the exact release or model version responsible, not inferred from when the report happened to arrive. Nothing beyond that correlation is assembled for a joint look. The client's own infrastructure team, or Acme AI engineering during a joint support session, reads the trace wherever it was forwarded.

The same tracing discipline extends to the materialization service's batch path. [`§ Engineering and Production Considerations § Orchestration`](#orchestration) describes the batch path as the other half of the orchestration engine, sharing "one set of retry, failure-handling, and scheduling semantics" with the live path. The batch path covers separate processes, not one, since they run on different cadences and neither is nested inside the other. Grid materialization gets one trace per business unit's materialization run. That matches the existing rule that at most one materialization run is in flight per business unit at a time ([`specs/application/technical/materialization-service/forecast-materialization.md § Forecast materialization`](/specs/application/technical/materialization-service/forecast-materialization.md#forecast-materialization)). Each grid cell, one competitor, geography, and horizon combination, gets its own child span, and the cells are computed in parallel. Each named step within a cell's computation gets its own span in turn: product matching, geography normalization, currency normalization, and forecast computation. The spans use the same named Algorithms and sections that [`specs/application/technical/materialization-service/reconciliation.md § Product and Geography Reconciliation`](/specs/application/technical/materialization-service/reconciliation.md#product-and-geography-reconciliation) already defines, not a second, separately maintained process description invented for tracing's sake. So a specific Effective Price Forecast row's data_vintage_id can be traced back to more than the inputs it used, which the Rationale Record already covers. It can be traced to how the computation that produced it ran: which step took how long, and whether anything retried. That is the same infrastructure-correlation benefit as the live path, applied to where a business user's forecast came from.

Document vectorization is a separate process, with its own trace per ingested document (or per corpus-refresh batch). The trace is independent of any specific grid cell, because a Driver Signal the process produces may feed many future cells' computations, or sit unused for months. The process follows the cadence of [`specs/application/technical/materialization-service/driver-signal-extraction.md § Vector and semantic mapping, with structured extraction`](/specs/application/technical/materialization-service/driver-signal-extraction.md#vector-and-semantic-mapping-with-structured-extraction), "the same cadence as the corpus refresh," not tied to a business unit's grid materialization run. That section reads every document first. It names distinct operations on each document that states an event in a driver category: the document is chunked, embedded, and extracted. These operations are separate spans, not one. Embedding and extraction are each their own model call. The registry ([`specs/application/technical/model-registry.md § Model registry`](/specs/application/technical/model-registry.md#model-registry)) names extraction as one of its LLM-based tools, a different model entirely from the one that embeds. So a slow or failed document is traceable to the operation responsible, whether chunking, the embedding call, or the extraction call, not just to "driver signal extraction" generically.

## Open Questions

**Records:**

- **Name:** Retry Policy
  **Open Question:** How many times is a failed step retried, and on what backoff, before the step counts as failed?
  **Provisional Answer:** On the live path, a failed step is retried up to twice, waiting 200 and then 400 milliseconds, so a failing step's waits add no more than 600 milliseconds to its latency budget. On the batch path, it is retried up to three times, waiting one, two and then four minutes. Both follow the one set of retry semantics the orchestration engine gives both paths, differing only in these values.
  **Impacts:** the Orchestration State Machine's failure states, [`§ Engineering and Production Considerations § Orchestration [States.State: predict_failed]`](#orchestration), [`§ Engineering and Production Considerations § Orchestration [States.State: position_failed]`](#orchestration) and [`§ Engineering and Production Considerations § Orchestration [States.State: simulate_failed]`](#orchestration), which it fixes once a step's retries are exhausted, and the one set of retry semantics both paths share ([`§ Engineering and Production Considerations § Orchestration`](#orchestration)); the live path's response time in the low seconds ([`§ Engineering and Production Considerations`](#engineering-and-production-considerations)); and when an answer degrades after exhausting its retries ([`specs/application/product/trust-and-explainability/degraded-answer-behavior.md § Degraded Answer Behavior`](/specs/application/product/trust-and-explainability/degraded-answer-behavior.md#degraded-answer-behavior)).

- **Name:** Retention Decrease
  **Open Question:** How is a genuine decrease to an installation's retention period made, and is it contract- and legal-reviewed?
  **Provisional Answer:** It is not made: the retention period only rises, through the control plane, and nothing shortens it.
  **Impacts:** the purge that relies on a period that never shrinks, in [`§ Engineering and Production Considerations § Security and governance [Step: 4]`](#security-and-governance) and that section's account of why comparing against today's setting never shortens a commitment; and the retention period's raise-only control ([`specs/application/technical/control-plane-service/control-plane.md § Control Plane`](/specs/application/technical/control-plane-service/control-plane.md#control-plane)).
