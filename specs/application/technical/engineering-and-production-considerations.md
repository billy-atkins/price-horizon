## Engineering and Production Considerations

**Data pipeline cadence —** batch ingestion for syndicated and POS data on a daily or weekly cycle, near-real-time ingestion for price-change signals that matter for a fast-moving competitive response, and a periodic re-embedding cycle for the qualitative corpus as new documents arrive. The forecast materialization job (`specs/application/technical/materialization-service/forecast-materialization.md § Forecast materialization`) runs immediately after each competitor data refresh, one of the triggers that section names, so the materialized grid is never more stale than its source.

**Latency and cost budget —** the scorecard and narrative layers need a response time in the low seconds to feel like a search box. The drill-down and full decomposition can tolerate more, since the user has already committed to exploring. Caching common question intents keeps the frequent questions fast and cheap without weakening the guarantee that an uncached query still runs the full pipeline.

**API shape —** a single REST API serves both the answer surface and the control plane, one auth model and one set of client libraries for both, the separation between them being the service boundary (`§ Engineering and Production Considerations § Service boundaries`), not the API surface. What a question request carries and what every answer returns about its business unit and kind of decision is `specs/application/technical/query-service/intent-and-retrieval.md § Dynamic Retrieval and Weighting (when the question is asked) § Session context`. JSON:API-style query conventions handle the answer surface's need to avoid over-fetching a deeply nested response: `include=` pulls in related resources in one round trip, dotted paths reaching into nested Positioning Candidates when needed (`include=positions.rationale,positions.simulatedOutcome`), and `fields[type]=` sparse fieldsets avoid pulling a full Rationale Record when a caller only needs a few fields. The performance work happens in the data layer, not the API: the Effective Price Forecast already bundles the fact and its rationale into one read, so an include or a field selection serves already-joined data, not a chain of separate lookups.

**Deployment and versioning —** `specs/application/product/platform-and-compliance-operations/deployment-topology.md` states the deployment topology and its per-business-unit configuration scoping; the business-unit-scoped rows of `specs/application/technical/control-plane-service/control-plane.md § Control Plane`'s Constraint table are the technical-specific configuration surface underneath that same scoping. The mechanism itself, the seeding and consolidation logic, the reconciliation approach, stays canonical across every installation, only its tuning is configuration.

Application and models version independently of each other. The application version covers the orchestration, the positioning engine's logic, the reconciliation mechanism, and the API and UI contracts. Each model and weighting rubric in the registry (`specs/application/technical/model-registry.md § Model registry`) versions on its own cadence, validated independently against the golden-question harness (`specs/application/technical/evaluation-and-monitoring.md § Evaluation and monitoring`). A customer can take an application upgrade without any model changing underneath them, or receive a recalibrated model without an application upgrade forcing new UI or workflow changes on them at the same time. Acme AI ships each as its own release; a customer's installation pins to a specific application version and a specific version of every model it calls, upgraded Acme AI-managed or self-managed, as `specs/application/product/platform-and-compliance-operations/versioned-upgrades.md § Versioned Upgrades` describes.

### Orchestration

Once a question is asked, the live-path pipeline needs a workflow layer built for retries, partial failure, and observability, not a single long prompt, each step independently testable. It is a fixed, deterministic sequence with parallel fan-out and fan-in, not a graph where a model decides the next step, so the right category of tool is a durable execution engine built for retryable pipelines, not an agent framework, the one `specs/application/technical/stack.md § Technical Stack` names, running both the query service's live path and the materialization service's batch path, on the cadence `specs/application/technical/materialization-service/forecast-materialization.md § Forecast materialization` sets, its runs started without any question being asked. The same orchestration engine for both is itself part of what keeps a live answer and a materialized one from ever disagreeing (`specs/application/technical/materialization-service/forecast-materialization.md § Forecast materialization`): one set of retry, failure-handling, and scheduling semantics, not separate tools whose behavior has to be kept in sync with each other.

States:

| state | description | terminal |
|---|---|---|
| intent_parsing | Question intent is parsed and decoupled against the governed glossary (`specs/application/technical/query-service/intent-and-retrieval.md § Dynamic Retrieval and Weighting (when the question is asked) § Intent parsing and decoupling`) | No |
| query_denied | No business unit in the user's IdP-asserted access grants this identity access to any business unit; the query is denied (`specs/application/technical/query-service/intent-and-retrieval.md § Dynamic Retrieval and Weighting (when the question is asked) § Intent parsing and decoupling`) | Yes |
| clarification_needed | Business unit access resolved ambiguously, an entity in the question does not resolve uniquely against the resolved business unit's glossary, or the kind of decision is unsettled; the pipeline stops and a clarifying question is returned instead of a forecast (`specs/application/technical/query-service/intent-and-retrieval.md § Dynamic Retrieval and Weighting (when the question is asked) § Intent parsing and decoupling`, `specs/application/product/trust-and-explainability/guarantees.md § Guarantees This Answer Engine Makes`) | Yes |
| parallel_retrieval | Evidence relevant to the resolved intent is retrieved across sources in parallel (`specs/application/technical/query-service/intent-and-retrieval.md § Dynamic Retrieval and Weighting (when the question is asked) § Parallel evidence retrieval`) | No |
| signal_routing | Retrieved driver signals are routed to baseline forecasting or driver attribution by event type (`specs/application/technical/predict-computation.md § Predict Computation § Signal routing`) | No |
| effective_price_forecasting | The baseline effective price forecast is computed (`specs/application/technical/predict-computation.md § Predict Computation § Effective price forecasting`) | No |
| triangulation | Retrieved Driver Signal records that could disagree with the baseline are selected, for driver_attribution to size and check (`specs/application/technical/predict-computation.md § Predict Computation § Triangulation and conflict checks`) | No |
| driver_attribution | Each driver's contribution is scored and added to the baseline, producing the published forecast and its flagged conflicts (`specs/application/technical/predict-computation.md § Predict Computation § Driver Attribution`) | No |
| confidence_and_rationale_packaging | The forecast's confidence score and rationale record are assembled (`specs/application/technical/predict-computation.md § Predict Computation § Confidence and rationale packaging`) | No |
| positioning_engine | Positioning candidates are generated from the forecast (`specs/application/technical/query-service/layered-output-synthesis.md § Layered Output Synthesis (producing the answer) § Positioning engine`) | No |
| simulation_engine | Each seeded positioning candidate's business outcome is simulated (`specs/application/technical/query-service/layered-output-synthesis.md § Layered Output Synthesis (producing the answer) § Simulation engine`) | No |
| option_consolidation | Adjacent candidates whose simulated outcomes do not materially differ are consolidated (`specs/application/technical/query-service/layered-output-synthesis.md § Layered Output Synthesis (producing the answer) § Option Consolidation`) | No |
| narrative_rendering | The full answer is rendered into plain language (`specs/application/technical/query-service/layered-output-synthesis.md § Layered Output Synthesis (producing the answer) § Narrative rendering`) | No |
| answer_produced | The forecast, its positioning options, and their simulated outcomes are returned | Yes |
| predict_failed | Retries are exhausted in intent_parsing, parallel_retrieval, signal_routing, effective_price_forecasting, triangulation, driver_attribution, or confidence_and_rationale_packaging before a forecast can be produced; intent_parsing's own successful branch outcomes, query_denied and clarification_needed, are not failures and never route here. No forecast is returned and no Delivered Answer record is created, the mechanism behind `specs/application/product/trust-and-explainability/degraded-answer-behavior.md § Degraded Answer Behavior`'s guarantee that a forecast that cannot be computed is reported honestly, never silently backfilled | Yes |
| position_failed | The forecast completed, but retries are exhausted in positioning_engine before any positioning candidate can be produced; the completed forecast is still returned, clearly labeled as missing Position and Simulate, the mechanism behind `specs/application/product/trust-and-explainability/degraded-answer-behavior.md § Degraded Answer Behavior`'s promise that a completed forecast is never withheld just because a later stage failed | Yes |
| simulate_failed | The forecast and positioning both completed, but retries are exhausted in simulation_engine or option_consolidation before simulated outcomes can be produced; the completed forecast and positioning options are still returned, clearly labeled as missing Simulate, the same guarantee (`specs/application/product/trust-and-explainability/degraded-answer-behavior.md § Degraded Answer Behavior`) applied one stage later | Yes |

Transitions:

| From | To | Guard or trigger |
|---|---|---|
| intent_parsing | query_denied | No business unit in the user's IdP-asserted access grants this identity access to any business unit |
| intent_parsing | clarification_needed | Business unit access resolves ambiguously, an entity does not resolve uniquely against the resolved business unit's glossary, or the kind of decision is unsettled |
| intent_parsing | parallel_retrieval | Business unit resolves, every entity resolves uniquely against its glossary, and the kind of decision is settled |
| parallel_retrieval | signal_routing | Retrieval completes |
| signal_routing | effective_price_forecasting | Routing completes |
| effective_price_forecasting | triangulation | Forecasting completes |
| triangulation | driver_attribution | Triangulation completes |
| driver_attribution | confidence_and_rationale_packaging | Attribution completes |
| confidence_and_rationale_packaging | positioning_engine | Packaging completes |
| positioning_engine | simulation_engine | Positioning completes |
| simulation_engine | option_consolidation | Simulation completes |
| option_consolidation | narrative_rendering | Consolidation completes |
| narrative_rendering | answer_produced | Rendering completes |
| intent_parsing, parallel_retrieval, signal_routing, effective_price_forecasting, triangulation, driver_attribution, confidence_and_rationale_packaging | predict_failed | Retries are exhausted before the state's own transition condition is met |
| positioning_engine | position_failed | Retries are exhausted before a positioning candidate is produced |
| simulation_engine, option_consolidation | simulate_failed | Retries are exhausted before simulated outcomes or consolidation complete |

`narrative_rendering` gets no failure state of its own: by the time it runs, Predict, Position, and Simulate have all already completed, so if prose generation itself fails, the answer falls back to the same structured facts, the forecast, the options, the simulated outcomes, rendered as plain labeled figures instead of generated prose, not withheld. `specs/application/technical/architecture.md § Architecture Overview § Diagrams § Orchestration State Machine` renders this State Machine, collapsed to that file's own altitude.

A Constraint on this State Machine's output:

| Constraint | Applies to | Enforced by |
|---|---|---|
| The pipeline never substitutes a stale materialized cell, or a previous run's positioning or simulation output, in place of a computation that could not be freshly completed | predict_failed, position_failed, simulate_failed | The orchestration engine's failure-handling semantics, which return one of these states instead |

This State Machine fixes the outcome once a step's retries are exhausted; how many retries a step gets is `§ Open Questions [Name: Retry Policy]`.

### Service boundaries

Separate services, not one, each justified by a different property rather than split for its own sake. The query service runs the live path (`specs/application/technical/query-service/intent-and-retrieval.md § Dynamic Retrieval and Weighting (when the question is asked)`, `specs/application/technical/predict-computation.md § Predict Computation`, and `specs/application/technical/query-service/layered-output-synthesis.md § Layered Output Synthesis (producing the answer)`), request-driven, held to the latency budget. The materialization service runs the batch path, forecast materialization, driver signal extraction, and product and geography reconciliation, throughput-oriented and tolerant of long-running jobs, with nothing in common operationally with an interactive request. The control plane service is separated for a security reason, not a workload reason: every operation on it writes configuration that governs every future answer, reference data, materiality thresholds, the IdP claim mapping itself, a categorically more sensitive surface than the query service's read-only path. Only the control plane service holds write credentials to the reference tables in `specs/application/technical/data-model.md § Core Data Model § Reference and Master Data`, the query service never does, so a vulnerability in the far larger, far more exposed query surface cannot reach the capability to change what a competitor's code means or what a business unit's threshold is. This is the mechanism behind the architectural separation `specs/application/product/roles.md § Roles § Using and Administering Kept Apart` states.

`specs/application/technical/architecture.md § Architecture Overview § Diagrams § Layer Composition` and `specs/application/technical/architecture.md § Architecture Overview § Diagrams § Trust Boundaries` render this.

### Security and governance

The primary control is deployment topology: each customer's data stays inside their own environment by construction, there is no shared store for it to leak through, save what the client lets a frontier model provider see (`specs/application/technical/model-registry.md § Model registry`). Acme AI's access as the operator is a secondary, governed layer, access control and audit logging, not a substitute for the residency decision itself. Within that environment, IdP-asserted claims (`specs/application/technical/identity-and-access.md § Business unit access, federated`) are the enforcement boundary, checked differently by different services and different stores: in the vector database, by the per-namespace credentials `specs/application/technical/secrets-management.md § Secrets management` issues the query service over the namespaces `specs/application/technical/data-model.md § Core Data Model § Harmonized quantitative foundation` partitions it into; in the structured database and the materialized grid, by the claim filter on every retrieval that `specs/application/technical/query-service/intent-and-retrieval.md § Dynamic Retrieval and Weighting (when the question is asked) § Intent parsing and decoupling` applies; and at the control plane service, by the Control plane admin claim check `specs/application/technical/identity-and-access.md § Business unit access, federated` describes, behind the write credentials `§ Engineering and Production Considerations § Service boundaries` confines to that service. Platform admin access, Acme AI's own, follows `specs/application/technical/identity-and-access.md § Platform admin access`, its break-glass credentials held in the vault `specs/application/technical/secrets-management.md § Secrets management` describes. Competitor pricing intelligence and licensed syndicated data both carry real contractual and competitive sensitivity on top of that, access control needs to reflect data licensing terms, and every generated answer needs an audit trail sufficient to defend it internally or to a retailer. `specs/application/technical/architecture.md § Architecture Overview § Diagrams § Trust Boundaries` renders this.

An Audit Log Entry (`specs/application/technical/data-model.md § Core Data Model § Audit Log § Audit Log Entry`) is application data, not a log in the observability sense, and it never touches the observability pipeline application logs flow through at all (this section's application logging passage). How the write actually happens: a middleware component, the same pattern by whichever name a given stack already calls it, ASP.NET Core-style middleware or an Action Filter, a Servlet Filter or Spring's HandlerInterceptor in a JVM stack, wraps every request, whether it is a Query user's own question, arriving through the UI or a direct API call, a Control plane admin's or an Identity admin's change through the control plane service, or a Platform admin action against the query, materialization, or control plane service (`§ Engineering and Production Considerations § Service boundaries`), the same pipeline for every one of them, rather than every individual action's own business logic needing to know it is being audited. Onboarding and upgrade are an exception to "every request": neither runs through any of those services' own request pipeline, so their own audit entries are written directly by Acme AI's internal provisioning and release tooling instead, joining that tooling's own transaction the same disciplined way, not the per-request middleware described here. Two entries record the installation's own activity rather than any request: a retention_purge entry, written by the purge run that this section's retention steps describe, and a frontier_models_changed entry, written by the control plane service as the installation starts (`specs/application/technical/model-registry.md § Model registry`). The middleware buffers the auditable fact in memory as the request is handled, then flushes it immediately before the response is returned, not fire-and-forget afterward, but not every audited action writes anything of its own to flush alongside: a diagnostic support session, viewing application logs, or reading the installation's pinned versions is genuinely read-only for Platform admin, with nothing else to join. A Query user's own question never is, regardless of path: the query service always persists a Delivered Answer (`specs/application/technical/data-model.md § Core Data Model § Pipeline and Answer Artifacts § Delivered Answer`) as the final step of producing any answer that reaches Predict, whether that same question's own Predict stage was a grid lookup, per `specs/application/technical/materialization-service/forecast-materialization.md § Forecast materialization`, or a live computation, so the flush always has at least that Delivered Answer write to join, on top of the audit write itself. Where the action itself writes something beyond its own Delivered Answer, onboarding, an upgrade, a configuration_changed edit against any of the self-service surfaces `specs/application/technical/control-plane-service/control-plane.md § Control Plane`'s own Constraint table names, or a question answered by a live computation that also persists its own Effective Price Forecast row, the audit entry joins that same database transaction alongside whichever of those writes actually applies, and if the transaction fails to commit for any reason, the audit write included, the whole request rolls back together, an action and its own audit entry are never separated. A configuration_changed entry against one of a business unit's settings that shape an answer, its dead-zone threshold, a materiality threshold, an archetype's display label, or the display name of one of its competitors, geographies or the business unit itself, is itself, on committing, what increments that business unit's `business_unit_configuration_version`; any other configuration_changed entry, among them a data source's credentials, a log threshold, a glossary alias or an IdP claim mapping, is audited the same way but raises no version (`specs/application/technical/data-model.md § Core Data Model § Pipeline and Answer Artifacts § Answer Provenance`), the same version every Effective Price Forecast row pins itself to, so every version bump is one specific, attributable audit entry, who changed what, from what value, to what value, and when, not just a number that changed. Where the action is genuinely read-only, a diagnostic session, viewing application logs, or reading the pinned versions, the audit write is the only write in the request, its own transaction, and it is that write's own success the response is gated on. A Query user's own question served straight from the grid is never this case: its own Delivered Answer and its audit entry are a pair, one transaction, gating the response together, the same guarantee. If the audit write itself fails, the request fails outright, the same way any other failure to complete an answer already does (`specs/application/product/trust-and-explainability/degraded-answer-behavior.md § Degraded Answer Behavior`): no forecast is shown, what is shown is that one could not be computed, and the Query user is told to try again, never an answer shown with no audit trail behind it, and never a stale or partial substitute offered in its place. Either way, an action can never be left recorded as having happened, or its results shown, with no audit trail behind it, nor an audit entry left behind for a write that itself rolled back. This is deliberate, not incidental: an audit record needs long retention, a stable, versioned schema, transactional certainty, and to stay queryable through the Control Plane's own self-service surface, none of which a general telemetry backend, OpenTelemetry-native or a client's own observability platform alike, is built to provide, and never a shared, Acme-AI-hosted store spanning multiple customers either, the same residency principle this section states. Retained for at least one year by default, a floor the installation-wide retention_period setting can be raised above per a client's own contractual requirement, a raise recorded the same way any other governed configuration_changed entry is and governed as `specs/application/technical/control-plane-service/control-plane.md § Control Plane` sets out, a genuine decrease being outside self-service and routine governed configuration entirely (`§ Open Questions [Name: Retention Decrease]`), and readable by both the client and Acme AI, but not through the same surface, and not the same slice of the table for everyone: a Control plane admin views every entry scoped to their own business unit, Acme AI's own access to it, every configuration_changed edit made within it regardless of which admin made it, and their own Query users' questions alike, plus an installation-wide entry such as a Platform admin's upgrade or an Identity admin's change to who holds the Platform admin role, through the same self-service Control Plane surface, and an Identity admin views every IdP claim mapping change across the installation, and every question denied because its asker's access held no business unit, through that same surface every other business-unit activity already goes through (`specs/application/product/tenant-administration/audit-log-visibility.md`), the mechanism behind that section's own promise that this is a record a client can actually see, not just trust happens somewhere out of sight; Acme AI views its own access, every configuration_changed edit, and every business unit's Query user activity across the installation, through its own internal engineering tooling, not through any PriceHorizon product screen, the same way Platform admin's other activities, onboarding, upgrades, diagnostic access, already work outside the client-facing product entirely.

Purging what has aged past retention_period runs on the nightly schedule materialization already keeps (`specs/application/technical/materialization-service/forecast-materialization.md § Forecast materialization`), reused rather than inventing a second rhythm this system runs on, by an Algorithm:

| Step | Action |
|---|---|
| 1 | For every Audit Log Entry whose action_type is not retention_purge, and which is not the latest frontier_models_changed entry, check whether occurred_at is older than the installation's current retention_period |
| 2 | If it is not, take no action, this entry is checked again on a later run |
| 3 | If it is, delete the entry, a hard delete, not an archive, since retaining compliance data longer than a stated purpose requires is its own exposure, not a safety margin; if the entry being purged has a delivered_answer_id, delete that Delivered Answer row in the same operation, since nothing else in the system ever references it once its own audit entry is gone |
| 4 | Record that this run happened as its own retention_purge entry, regardless of whether any entry actually qualified for deletion that night |

Step 1's own exclusion is deliberate: a retention_purge entry, the run's own record of itself, is never a candidate for its own deletion regardless of age, since it is what proves the process has been running compliantly over time, and the reason to keep it never diminishes the way an old access record's own relevance does; its own volume, one entry per run, never per business action, makes an exception worth making rather than a loophole worth closing. The latest frontier_models_changed entry is kept for a reason of the same kind: it records which kinds of model call the installation now lets reach a frontier model provider, and is what the next change is recorded against (`specs/application/technical/model-registry.md § Model registry`), so it is never deleted while it is the latest, and is deleted as any other entry once a later one replaces it and its own age passes the retention period. Because retention_period can only be raised through this design (`specs/application/technical/control-plane-service/control-plane.md § Control Plane`, `§ Open Questions [Name: Retention Decrease]`), the "current retention_period" step 1 checks against is always the longest that has ever applied, so comparing every entry against today's setting, rather than against whatever setting happened to be in effect the day it was written, never retroactively shortens a commitment already made; a raise takes effect immediately, protecting entries that would otherwise have aged out under the old, shorter setting, exactly the outcome a client extending their own retention requirement expects.

Further capabilities follow directly from fields already on this entry, not from any new mechanism, and exist specifically so this audit trail can be used under pressure, not just consulted after the fact. One: verifying the repeatability guarantee (`specs/application/product/trust-and-explainability/guarantees.md § Guarantees This Answer Engine Makes`) in production is a matter of comparing two question_asked entries for what looks like the same question, side by side, on their referenced Delivered Answer's own Effective Price Forecast, and that forecast's own pinned key, competitor, business unit, geography, horizon, data_vintage_id, application_version, model_versions, and business_unit_configuration_version (`specs/application/technical/data-model.md § Core Data Model § Pipeline and Answer Artifacts § Effective Price Forecast`); an identical key with a different forecast value is a genuine defect worth escalating, an identical key with an identical forecast value confirms the guarantee held, and a changed key, a data refresh landed, or a configuration_changed entry bumped the version in between, explains a legitimate difference rather than leaving it looking like an unexplained one, the configuration_changed entry being exactly what makes that explanation traceable to a specific edit rather than an inference. Another: investigating a non-technical executive's complaint about what they were told never depends on recomputing anything. What Position and Simulate actually produced, and the exact application and model versions that produced it, is captured directly instead, on that same Delivered Answer record, alongside the forecast reference and the rendered narrative, so every piece of one delivered answer lives in one row, referenced as a whole by `delivered_answer_id`. A question_asked entry's `delivered_answer_id` points to the one record holding every piece together; nothing about a past answer ever needs to be recomputed to know what it was.

A retained record measured in years is only as useful as someone's ability to find one entry inside it, and that turns out to be a narrower problem than a general log search engine solves, because every field on this schema is already structured, a foreign key, an enum, a timestamp, never an unstructured line of text parsed and indexed after the fact. Filtering by actor, action_type, occurred_at as a bounded time range, and, for a question_asked entry, the competitor and geography named on its referenced Delivered Answer's own Effective Price Forecast, or, for a configuration_changed entry, its own changed_field, is therefore ordinary indexed-column filtering against the same structured database this table already lives in, ranges and exact matches on values already known, not a purpose-built search index bolted on top. The referenced Delivered Answer's own `rendered_narrative` is the one field genuinely free text, natural language by nature, and it is the only field keyword search runs against. A filtered view defaults to a recent window, thirty days, rather than the full retention period, with a visible count of matching entries by day across that window, so a reviewer sees where activity actually clusters, a spike in query_denied outcomes, or several configuration_changed edits within the same hour, before reading a single row rather than only after stumbling onto it, the same reason bulk forecast review (`specs/application/product/accuracy-governance.md § Tracking Forecast Accuracy`) shows a pattern across many forecasts at once rather than one at a time. Selecting an entry expands its own full detail without losing the current filter, the referenced Delivered Answer, its positioning candidates, simulated outcomes, and rendered narrative together, and a link into the evidence already exposed for its referenced forecast (`specs/application/product/answer-engine/predict.md § Predict — what will the competitor do`), the same "without leaving the analysis" pattern that section's own evidence drill-down already establishes, extended here to an audit entry's own detail rather than invented separately for it. The filtered set itself, exactly the rows actually matching, never a capped sample, can be exported to a flat file, the form this record most often actually needs to take to leave the product, handed to an auditor, legal, or the client's own security team, none of whom need a PriceHorizon login of their own to receive it, but the export never carries a referenced Delivered Answer's own content, only the `delivered_answer_id` reference itself: that record exists specifically because it restates an answer's own protected substance directly rather than by reference, and a flat file leaving the product entirely is exactly the uncontrolled destination that substance was never allowed to reach anywhere else in this design. Viewing it stays possible, in place, through the governed surfaces this section describes, an export just never carries it with it.

Application logging (`specs/application/product/logging-and-traceability.md § Logging and Traceability § Application Log`) is a distinct concern from the audit log, debugging why a step actually failed, not who accessed what, and it covers the application only: infrastructure, the servers, network, and storage PriceHorizon happens to run on, is the client's own infrastructure team's responsibility, monitored with whatever tooling they already run in their own environment, since PriceHorizon is self-hosted inside it, never Acme-AI-hosted (`specs/application/product/platform-and-compliance-operations/deployment-topology.md`). The application's OpenTelemetry signals, traces, logs and metrics alike, never carry the categories of protected content, a forecast's actual quantitative values, a Driver Signal's document content, credential material, or a raw IdP claim payload. Every entry and trace does carry the Query user's own identity, the same claim already resolved during intent parsing, so a specific executive's reported issue can be traced to its own logs directly, and the application_version that produced it, since that version keeps changing over successive releases and a log line without it cannot be placed against which release actually behaved that way. Application log content has no PriceHorizon product screen at all, for either role: a Control plane admin can raise the threshold that controls how much gets captured (`specs/application/product/tenant-administration/application-log-control.md`), but never reads the resulting content themselves, that isn't what their self-service surface is for. The application writes its own structured log lines, spans and metrics to standard output or a log file, the ordinary mechanism for a self-hosted application, not a custom export path of its own; a standard forwarding agent deployed within the installation tails that output and forwards it to whatever observability platform the client already runs, rather than Acme AI standing up a redundant tool inside an environment the client already instruments, the same "the client already has infrastructure tooling of its own" reasoning, now extended to the application layer; where a client has no platform of their own, that same agent forwards instead to a self-hosted, OpenTelemetry-compatible viewer shipped alongside PriceHorizon as the fallback default. Either way PriceHorizon requires no connection outside the client's own environment; where the client's own platform runs is the client's choice. PriceHorizon never sends any of it to anything Acme AI hosts, and never combines it with another customer's. How Acme AI engineering actually gets access to view it differs by which path applies, and so does what PriceHorizon's own audit trail can see of it: into the client's own platform, whatever the client grants there is the client's own process, outside PriceHorizon's own access model to define, and outside its own Audit Log to observe, PriceHorizon has no visibility into an access that never touches it, a real limit on what the audit trail can promise to cover, stated as a boundary on that same promise in `specs/application/product/tenant-administration/audit-log-visibility.md § Audit Log Visibility` rather than left implicit here alone. Scoping whatever credential a business unit grants there to what a specific issue's triage actually needs, rather than a standing account, is the business unit's own responsibility to hold; PriceHorizon has no way to verify or enforce that scoping, since the grant happens entirely outside it, the same way it has no visibility into the access itself; into the fallback viewer, Platform admin's own governed access path, federated claim or break-glass credentials (`specs/application/technical/identity-and-access.md § Platform admin access`), the same one that authenticates every other Platform admin activity, itself generating its own Audit Log Entry (`specs/application/technical/data-model.md § Core Data Model § Audit Log § Audit Log Entry`) the moment it's used, not a second, separately managed credential just for observability. The application's metrics, request counts, latency percentiles, retry and failure rates behind `§ Engineering and Production Considerations § Orchestration`'s own predict_failed, position_failed, and simulate_failed states, carry no business content by construction. Traces, logs, and these metrics alike are retained on an operational cadence, weeks not years, long enough to debug a recently reported issue, not a compliance record.

Every log entry is written at one of the standard levels, in decreasing order of verbosity: trace, every step, most detail, suited to active debugging, debug, info, the default for normal operation, and error, only genuine failures, the same severity scale OpenTelemetry's own logging data model already uses. Control over the threshold is asymmetric, not shared equally, matching where the rest of this architecture already draws the line between a business-unit fact and the underlying mechanism (`specs/application/product/tenant-administration/application-log-control.md`), and who may change which threshold is `specs/application/technical/control-plane-service/control-plane.md § Control Plane`'s: a Control plane admin lowers their own business unit's toward trace when they want Acme AI to have more detail to resolve an issue they're experiencing without needing to ask first, the same self-service philosophy already behind triggering an out-of-cycle materialization run, and a Platform admin's installation-wide default and override serve deeper, cross-cutting debugging, the mechanism itself staying with Acme AI the same reason the archetype rules and weighting rubrics do.

The mechanism is traces and spans, not just discrete log events: each state in the Orchestration State Machine (`§ Engineering and Production Considerations § Orchestration`) is its own span, intent_parsing, parallel_retrieval, signal_routing, and so on through to answer_produced or one of the failure states, and a full run from intent_parsing onward is one trace, giving a request's actual path and per-step timing through the pipeline, not just a list of events about it. Each span carries the standard OpenTelemetry resource attributes identifying the infrastructure it ran on, host, container, or pod, whichever unit the client's own infrastructure team already monitors, so a slow or failed trace can be correlated against that infrastructure's own performance at the same moment, without Acme AI ever collecting or operating that infrastructure monitoring itself, the same boundary this section draws. Every span also carries the application_version that ran it, and any span whose own state actually invokes a versioned model, forecast computation, driver attribution, the positioning archetype rule, a simulation model, embedding, or extraction, carries that specific model's own registry version too (`specs/application/technical/model-registry.md § Model registry`), the same versions already pinned on a persisted Effective Price Forecast row or captured directly for Position and Simulate, now attached to the trace that produced them as well, so a behavior change noticed months later in a debugging session can be pinned to the exact release or model version responsible rather than inferred from when the report happened to arrive. Nothing beyond that correlation is assembled for a joint look: the client's own infrastructure team, or Acme AI engineering during a joint support session, reads the trace wherever it was forwarded.

The same tracing discipline extends to the materialization service's batch path, the other half of the orchestration engine `§ Engineering and Production Considerations § Orchestration` already describes as sharing "one set of retry, failure-handling, and scheduling semantics" with the live path, and it covers genuinely separate processes, not one, since they run on different cadences and neither is nested inside the other. Grid materialization gets one trace per business unit's materialization run, matching the existing rule that at most one materialization run is in flight per business unit at a time (`specs/application/technical/materialization-service/forecast-materialization.md § Forecast materialization`); each grid cell, one competitor, geography, and horizon combination, its own child span computed in parallel; and each named step within a cell's own computation, product matching, geography normalization, currency normalization, forecast computation, its own span in turn, using the same named Algorithms and sections `specs/application/technical/materialization-service/reconciliation.md § Product and Geography Reconciliation` already defines rather than a second, separately maintained process description invented for tracing's sake. This is what lets a specific Effective Price Forecast row's own data_vintage_id be traced back not just to what inputs it used, the Rationale Record already covers that, but to how the computation that produced it actually ran, which step took how long, whether anything retried, the same infrastructure-correlation benefit as the live path, applied to where a business user's own forecast actually came from.

Document vectorization is a separate process, its own trace per ingested document (or per corpus-refresh batch), independent of any specific grid cell, since a Driver Signal it produces may feed many future cells' computations, or sit unused for months, per `specs/application/technical/materialization-service/driver-signal-extraction.md § Vector and semantic mapping, with structured extraction`'s own cadence, "the same cadence as the corpus refresh," not tied to a business unit's grid materialization run. That section reads every document first, and names distinct operations on each one that states an event in a driver category, chunked, embedded, and extracted, and they are separate spans, not one: embedding and extraction are each their own model call, extraction specifically named as one of the LLM-based tools in the registry (`specs/application/technical/model-registry.md § Model registry`), a different model entirely from the one that embeds, so a slow or failed document is traceable to the specific operation actually responsible, chunking, the embedding call, or the extraction call, not just to "driver signal extraction" generically.

## Open Questions

**Records:**

- **Name:** Retry Policy
  **Open Question:** How many times is a failed step retried, and on what backoff, before the step counts as failed?
  **Provisional Answer:** On the live path, a failed step is retried up to twice, waiting 200 and then 400 milliseconds, so a failing step's waits add no more than 600 milliseconds to its latency budget. On the batch path, it is retried up to three times, waiting one, two and then four minutes. Both follow the one set of retry semantics the orchestration engine gives both paths, differing only in these values.
  **Impacts:** the Orchestration State Machine's failure states, what it fixes once a step's retries are exhausted, and the one set of retry semantics both paths share (`§ Engineering and Production Considerations § Orchestration`); the live path's response time in the low seconds (`§ Engineering and Production Considerations`); and when an answer degrades after exhausting its retries (`specs/application/product/trust-and-explainability/degraded-answer-behavior.md § Degraded Answer Behavior`).

- **Name:** Retention Decrease
  **Open Question:** How is a genuine decrease to an installation's retention period made, and is it contract- and legal-reviewed?
  **Provisional Answer:** It is not made: the retention period only rises, through the control plane, and nothing shortens it.
  **Impacts:** the purge that relies on a period that never shrinks, in step 1 of the Algorithm in `§ Engineering and Production Considerations § Security and governance` and that section's account of why comparing against today's setting never shortens a commitment; and the retention period's raise-only control (`specs/application/technical/control-plane-service/control-plane.md § Control Plane`).
