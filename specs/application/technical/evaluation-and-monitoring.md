## Evaluation and monitoring

A golden question is a curated input scenario paired with an assertion about a structural property the answer must have. It makes no claim about what a real-world forecast will turn out to be. When a golden question is written, no ground truth exists for the forecast. Ground truth exists only for what the system's own declared rules promise the system will do with that input. A Decision Table's rows, an Algorithm's steps, a State Machine's states, and a Constraint's invariant can each be checked. A golden question is that check, exercised end to end through the running system rather than read off the page. A new row in a Decision Table, a new step in an Algorithm, or a new Constraint gets at least one golden question engineered to exercise it. Whoever adds the row, step, or Constraint adds the golden question, the same discipline as writing a test alongside new code. No separate curatorial role adds it.

For example, a question engineered to produce exactly one flagged conflict asserts that the confidence scoring Constraint's ceiling caps the score ([`specs/application/technical/predict-computation.md § Predict Computation § Confidence and rationale package § A flagged conflict's ceiling`](/specs/application/technical/predict-computation.md#a-flagged-conflicts-ceiling)). It does not assert that the resulting number matches any claimed real-world truth. The suite runs in CI whenever a model, prompt template, or data pipeline version changes. Every assertion has to hold before that version ships.

This suite does not validate forecast accuracy against what happened. That validation needs real, observed outcomes collected over time, and [`specs/application/technical/materialization-service/forecast-materialization.md § Realized outcome check`](/specs/application/technical/materialization-service/forecast-materialization.md#realized-outcome-check) is the mechanism for it. Nor is this suite the same thing as the product spec's Gherkin scenarios ([`specs/application/product/answer-engine/predict.md`](/specs/application/product/answer-engine/predict.md), [`specs/application/product/answer-engine/position.md`](/specs/application/product/answer-engine/position.md), [`specs/application/product/answer-engine/simulate.md`](/specs/application/product/answer-engine/simulate.md), [`specs/application/product/answer-engine/drill-down.md`](/specs/application/product/answer-engine/drill-down.md), and every other product capability, each with its own `Test Scenarios` section). Those scenarios are black-box checks that a capability delivers what it promises to a user, whichever internal mechanism produced it. This suite is white-box. It checks that one specific mechanism, such as a Decision Table row, an Algorithm step, or a Constraint, fires correctly. Both kinds of check matter, and neither substitutes for the other.

Beyond the golden-question regression suite, the human review queue for upstream data quality ([`specs/application/technical/data-model.md § Core Data Model § Pipeline and Answer Artifacts § Review Queue Item`](/specs/application/technical/data-model.md#review-queue-item)) and drift monitoring on the underlying models keep the system honest as data and markets shift. Drift monitoring watches the trend in forecast_error across accumulated Realized Outcomes ([`specs/application/technical/materialization-service/forecast-materialization.md § Open Questions [Name: Recalibration]`](/specs/application/technical/materialization-service/forecast-materialization.md#open-questions)), so it is more than a named intention. An elasticity model trained on pre-inflation data is not the same model six quarters later.
