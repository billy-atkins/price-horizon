## Evaluation and monitoring

A golden question is a curated input scenario paired with an assertion about a structural property the answer must have, not a claim about what a real-world forecast will turn out to be, there is no ground truth for a forecast at the time a golden question is written, only for what the system's own declared rules promise it will do with that input. A Decision Table's rows, a Decision Tree's branches, an Algorithm's steps, a State Machine's states, and a Constraint's invariant can each be checked; a golden question is that check, exercised end to end through the running system rather than read off the page. A new row in a Decision Table, a new branch in a Decision Tree, a new step in an Algorithm, or a new Constraint gets at least one golden question engineered to exercise it, added by whoever adds the row, branch, step, or Constraint, the same discipline as writing a test alongside new code, not a separate curatorial role.

A representative example: a question engineered to produce exactly one flagged conflict asserts that the confidence scoring Constraint's ceiling actually caps the score (`specs/application/technical/predict-computation.md § Predict Computation § Confidence and rationale packaging § A flagged conflict's ceiling`), not that the resulting number matches any claimed real-world truth. The suite runs in CI whenever a model, prompt template, or data pipeline version changes, and every assertion has to hold before that version ships.

This is deliberately not the same thing as validating forecast accuracy against what actually happened, that needs real, observed outcomes collected over time, which `specs/application/technical/materialization-service/forecast-materialization.md § Realized outcome tracking` is the mechanism for, not this suite. It is also deliberately not the same thing as the product spec's own Gherkin scenarios (`specs/application/product/answer-engine/predict.md`, `specs/application/product/answer-engine/position.md`, `specs/application/product/answer-engine/simulate.md`, `specs/application/product/answer-engine/drill-down.md`, and every other product capability, each with its own `Test Scenarios` section): those are black-box checks that a capability delivers what it promises to a user, regardless of which internal mechanism produced it; this suite is white-box, checking that one specific mechanism, a Decision Table row, an Algorithm step, a Constraint, actually fires correctly. Both matter, and neither substitutes for the other. Beyond the golden-question regression suite, the human review queue for upstream data quality (`specs/application/technical/data-model.md § Core Data Model § Pipeline and Answer Artifacts § Review Queue Item`) and drift monitoring on the underlying models, watching the trend in forecast_error across accumulated Realized Outcomes (`specs/application/technical/materialization-service/forecast-materialization.md § Open Questions [Name: Recalibration]`), not just a named intention (an elasticity model trained on pre-inflation data is not the same model six quarters later), keep the system honest as data and markets shift.
