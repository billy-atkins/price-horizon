## Business unit access, federated

Identity federates from the customer's own IdP, per [`specs/application/product/identity-and-access/identity-federation.md § Identity Federation`](/specs/application/product/identity-and-access/identity-federation.md#identity-federation). PriceHorizon does not pick an IdP and ask every customer to bridge it. The customer's own IdP sits inside the customer's own environment, so federating with it needs no connection outside that environment. An installation can therefore run entirely within the customer's security boundary, as [`specs/application/product/platform-and-compliance-operations/deployment-topology.md § Deployment Topology`](/specs/application/product/platform-and-compliance-operations/deployment-topology.md#deployment-topology) promises. The IdP asserts claims or group memberships. A governed IdP Claim Mapping ([`specs/application/technical/data-model.md § Core Data Model § Reference and Master Data § IdP Claim Mapping`](/specs/application/technical/data-model.md#idp-claim-mapping)) translates the customer's own claim values into a business unit and one of the roles [`specs/application/product/roles.md § Roles`](/specs/application/product/roles.md#roles) defines. The mapping is the same kind of crosswalk as [`specs/application/technical/materialization-service/reconciliation.md § Product and Geography Reconciliation`](/specs/application/technical/materialization-service/reconciliation.md#product-and-geography-reconciliation): someone else's identifiers reconciled to this system's own, established once during onboarding, not resolved per query.

Intent parsing, described in [`specs/application/technical/query-service/intent-and-retrieval.md § Dynamic Retrieval and Weighting (when the question is asked)`](/specs/application/technical/query-service/intent-and-retrieval.md#dynamic-retrieval-and-weighting-when-the-question-is-asked), checks a Query user claim. A Control plane admin's ordinary grant applies to an existing unit. For a new unit, the installation checks a separate client-controlled creation permission on the authenticated Control plane admin. Its scope covers the unit registration described in [`specs/application/product/tenant-administration/reference-data-management.md § Reference Data Management`](/specs/application/product/tenant-administration/reference-data-management.md#reference-data-management). The transaction creates the unit and its audit event without inserting a membership or role grant. A repeated request with the same identity and operation identifier returns the committed result. The control plane service ([`specs/application/technical/engineering-and-production-considerations.md § Engineering and Production Considerations`](/specs/application/technical/engineering-and-production-considerations.md#engineering-and-production-considerations)) checks the claim against whichever business unit's reference data or configuration a request tries to write. An admin for one business unit cannot write another's, even when the admin's token also grants query access to it. An Identity admin claim is scoped to no single business unit, for the same reason [`specs/application/product/roles.md § Roles`](/specs/application/product/roles.md#roles) gives that role. [`specs/application/technical/control-plane-service/control-plane.md § Control Plane § Configuration change path`](/specs/application/technical/control-plane-service/control-plane.md#configuration-change-path) requires the Identity admin claim for editing the claim mapping itself, the self-service capability [`specs/application/product/identity-and-access/identity-administration.md § Identity Administration`](/specs/application/product/identity-and-access/identity-administration.md#identity-administration) describes. Platform admin, the remaining role, is described in [`§ Platform admin access`](#platform-admin-access).

[`specs/application/technical/architecture.md § Architecture Overview § Diagrams § Layer Composition`](/specs/application/technical/architecture.md#layer-composition) and [`specs/application/technical/architecture.md § Architecture Overview § Diagrams § Trust Boundaries`](/specs/application/technical/architecture.md#trust-boundaries) render this.

## Platform admin access

[`specs/application/product/roles.md § Roles`](/specs/application/product/roles.md#roles) defines this role's scope: Acme AI's own staff, never the client's business configuration. The role federates only through the client's own IdP, never through an identity service Acme AI runs. Reaching outbound to such a service would work against the residency and governed-access principles this design is built on. It would also be unavailable to any client whose network posture forbids it. Each customer's data stays inside their own environment by construction ([`specs/application/technical/engineering-and-production-considerations.md § Engineering and Production Considerations § Security and governance`](/specs/application/technical/engineering-and-production-considerations.md#security-and-governance)). That same self-hosted topology puts network posture in the customer's hands, not Acme AI's, so both of this role's access paths stay inside the customer's environment.

A named Acme AI operator obtains the installation-wide Platform admin claim through the client's own identity provider. When that provider is unreachable, the operator authenticates locally with the installation's break-glass credential ([`specs/application/technical/secrets-management.md § Secrets management`](/specs/application/technical/secrets-management.md#secrets-management)). Both identities remain subject to the client's installation-wide support permission under [`specs/application/product/platform-and-compliance-operations/deployment-topology.md § Deployment Topology`](/specs/application/product/platform-and-compliance-operations/deployment-topology.md#deployment-topology).

The client's infrastructure team alone can change this permission, using customer-controlled local administration even during an identity-provider outage. The installation durably advances the permission generation on withdrawal. Each service enforces the current permission and generation at sign-in and on every privileged operation, including operations through support tooling. Withdrawal also terminates live privileged streams before they can deliver further data. A service that cannot establish the current permission and generation denies access. Restoring support requires a fresh sign-in. Identity-provider recovery and installation restarts preserve the client's choice.

Support permission is confirmed only when the installation can establish both the enabled setting and its current generation. For sign-in, evidence is valid when the client’s reachable identity provider authenticates the named operator, or when that provider is unreachable and the installation verifies the vault credential. For a protected action, valid evidence is a live support session of the current generation.

**Construct:** `specs/methodology/modeling-constructs.md § Constructs § Decision Table` \
**Conditions:** Permission confirmed?, Action, Evidence valid?

| Permission confirmed? | Action | Evidence valid? | Support access |
|---|---|---|---|
| false | - | - | Deny |
| true | - | false | Deny |
| true | New sign-in | true | Issue a support session for the current permission generation |
| true | Protected action | true | Allow within the Platform admin scope |
