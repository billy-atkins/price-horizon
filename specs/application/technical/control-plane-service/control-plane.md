## Control Plane

The control plane is a named capability, not a configuration file. It is the client-facing surface ([`specs/application/product/tenant-administration/reference-data-management.md`](/specs/application/product/tenant-administration/reference-data-management.md), [`specs/application/product/tenant-administration/business-unit-settings.md`](/specs/application/product/tenant-administration/business-unit-settings.md), [`specs/application/product/tenant-administration/data-source-connections.md`](/specs/application/product/tenant-administration/data-source-connections.md), [`specs/application/product/tenant-administration/review-queues.md`](/specs/application/product/tenant-administration/review-queues.md), [`specs/application/product/tenant-administration/audit-log-visibility.md`](/specs/application/product/tenant-administration/audit-log-visibility.md), [`specs/application/product/tenant-administration/application-log-control.md`](/specs/application/product/tenant-administration/application-log-control.md)) for managing everything in [`specs/application/technical/data-model.md § Core Data Model`](/specs/application/technical/data-model.md#core-data-model) that varies by business unit, without involving Acme AI in routine changes. It draws the same line as [`specs/application/technical/engineering-and-production-considerations.md § Engineering and Production Considerations`](/specs/application/technical/engineering-and-production-considerations.md#engineering-and-production-considerations): mechanism stays canonical, and tuning is configuration. A Decision Table over the configuration surfaces states that line ([`§ Control Plane § Configuration change path`](#configuration-change-path)).

The control plane service also serves read-only views of installation-wide values. The views [`specs/application/product/platform-and-compliance-operations/versioned-upgrades.md § Versioned Upgrades`](/specs/application/product/platform-and-compliance-operations/versioned-upgrades.md#versioned-upgrades) promises show the application version the installation is pinned to and each model's pinned version ([`specs/application/technical/engineering-and-production-considerations.md § Engineering and Production Considerations`](/specs/application/technical/engineering-and-production-considerations.md#engineering-and-production-considerations)). A Control plane admin reads them on this surface, and a Platform admin reads them through Acme AI's own tooling. The view [`specs/application/product/tenant-administration/audit-log-visibility.md § Audit Log Visibility`](/specs/application/product/tenant-administration/audit-log-visibility.md#audit-log-visibility) promises shows the audit log's retention_period currently in effect, and a Control plane admin reads it on this surface. The view [`specs/application/product/platform-and-compliance-operations/deployment-topology.md § Deployment Topology § Frontier Models`](/specs/application/product/platform-and-compliance-operations/deployment-topology.md#frontier-models) promises shows the kinds of model call the installation's configuration lets reach a frontier model provider ([`specs/application/technical/model-registry.md § Model registry`](/specs/application/technical/model-registry.md#model-registry)). A Control plane admin reads it on this surface too. Any Control plane admin claim reads the same installation-wide value, whichever business unit the claim is scoped to. No view can change what it shows. A Platform admin's read is Acme AI access through PriceHorizon's systems, recorded in the audit log like any other ([`specs/application/technical/engineering-and-production-considerations.md § Engineering and Production Considerations § Security and governance`](/specs/application/technical/engineering-and-production-considerations.md#security-and-governance)); a Control plane admin's is not.

[`specs/application/technical/architecture.md § Architecture Overview § Diagrams § Layer Composition`](/specs/application/technical/architecture.md#layer-composition) renders this.

Each self-service operation has a defined scope:
- **Reference data.** The admin can add or disable tracked reference data and change the display labels in their unit. A competitor rename writes the [`specs/application/technical/data-model.md § Core Data Model § Reference and Master Data § Business unit competitor label`](/specs/application/technical/data-model.md#business-unit-competitor-label) for the authorized unit and shared competitor. Every tracked brand of that competitor in the unit uses this label at the effective configuration version. A code locks at first use by ingested data. For a later source-code correction, register an alias against the existing row under [`specs/application/technical/data-model.md § Core Data Model § Reference and Master Data § Entity Alias`](/specs/application/technical/data-model.md#entity-alias). Geography registration uses the unit covered by the admin’s claim. A new Geography entry specifies either its parent in the hierarchy or, for a country-level entry with no parent, its own currency, for the reason the currency field of [`specs/application/technical/data-model.md § Core Data Model § Reference and Master Data § Geography`](/specs/application/technical/data-model.md#geography) gives.
- **Materiality and dead-zone thresholds.** These thresholds are set within bounds Acme AI provides as defaults ([`specs/application/product/tenant-administration/business-unit-settings.md § Business Unit Settings`](/specs/application/product/tenant-administration/business-unit-settings.md#business-unit-settings); for the materiality thresholds, [`specs/application/technical/query-service/layered-output-synthesis.md § Open Questions [Name: Default Materiality Thresholds]`](/specs/application/technical/query-service/layered-output-synthesis.md#open-questions)).
- **The application log threshold.** A Control plane admin can temporarily lower the threshold for the unit’s own traffic ([`specs/application/product/tenant-administration/application-log-control.md § Application Log Control`](/specs/application/product/tenant-administration/application-log-control.md#application-log-control)).

The control plane serializes governed changes to the installation’s retention_period with each purge deletion ([`specs/application/technical/engineering-and-production-considerations.md § Engineering and Production Considerations § Security and governance § Audit log purge`](/specs/application/technical/engineering-and-production-considerations.md#audit-log-purge)). It compares the submitted period with the committed setting and records an authorized change with its audit event in the same transaction. [`specs/application/technical/engineering-and-production-considerations.md § Open Questions [Name: Retention Decrease]`](/specs/application/technical/engineering-and-production-considerations.md#open-questions) governs requests for a shorter period.

#### Temporary business-unit logging

On an authorized increase, persist the request identity, unit, requested threshold, activation time and absolute UTC deadline together. The deadline is the activation time plus the window specified in [`specs/application/product/tenant-administration/application-log-control.md § Application Log Control`](/specs/application/product/tenant-administration/application-log-control.md#application-log-control). Return the deadline to the administrator. A retry of that request reuses the original result, even after restart or expiry. Replacing an elevation requires a fresh authorized request.

Resolve the effective threshold for the traffic’s business unit whenever detail is emitted. Use the current UTC time and the currently applicable installation settings. At the deadline the elevation has expired. Cleanup may remove only the expired activation it observed, so delayed cleanup cannot clear a replacement.

**Construct:** `specs/methodology/modeling-constructs.md § Constructs § Decision Table` \
**Conditions:** Platform override applies?, Unit elevation recorded?, Before its deadline?

| Platform override applies? | Unit elevation recorded? | Before its deadline? | Effective threshold |
|---|---|---|---|
| true | - | - | Platform override |
| false | false | - | Applicable baseline |
| false | true | false | Applicable baseline |
| false | true | true | Requested unit threshold |

The applicable baseline is the current installation default for that unit. An authorized platform override takes precedence for as long as it applies.

### External model routing changes

The client’s infrastructure team records each accepted change as a durable, monotonically numbered installation configuration revision containing the complete set of (call kind, provider, dated model version) tuples, sorted by call kind. Only the client can write these revisions. It retains each one until the audit store acknowledges it, including a withdrawal to an empty set. The control plane service reads this configuration at startup and reconciles pending revisions in order. [`specs/application/technical/model-registry.md § Model registry`](/specs/application/technical/model-registry.md#model-registry) defines the eligible calls and the input each may send.

The installation compares complete sets, including the empty set. It first takes the prior state from its durable checkpoint or, at migration, the most recent retained effective record in installation order. Confirmed first use supplies a known empty prior. A record with missing provider identities preserves the known kinds and dates and marks each absent provider unknown. Where prior evidence is missing and first use cannot be established, the entire prior state is unknown. An empty state observed after withdrawal supersedes every older nonempty state.

#### Routing revision history

For each accepted revision in sequence, the prior state is qualified when every prior route has a known provider and dated version. A known empty set is qualified. A legacy baseline identifies the first observed complete set and preserves the available prior evidence without assigning a time to any unobserved switch.

**Construct:** `specs/methodology/modeling-constructs.md § Constructs § Decision Table` \
**Conditions:** Prior state qualified?, Prior and observed sets equal?

| Prior state qualified? | Prior and observed sets equal? | Audit action |
|---|---|---|
| false | - | Record the first qualified baseline |
| true | true | Keep the existing history |
| true | false | Record the change from the prior set to the observed set |

In one installation database transaction the control plane service performs the audit action, writing frontier_models_changed when an entry is due, and advances the checkpoint to the acknowledged revision and observed set. It serializes competing recorders, skips revisions already acknowledged, and retains the checkpoint across audit retention. Withdrawal and restoration are separate revisions even if restoration returns to the original set.

#### External call authorization

A withdrawal takes effect immediately. Each service checks the current client permission at dispatch. Reconciliation is current only after the entire ordered sequence through the current client revision has been acknowledged, including any required audit entry. An unavailable permission, an unknown checkpoint, a gap or an unrecorded change keeps external routing closed across restarts. The destination matches only when both the current client configuration and the acknowledged set authorize the exact call kind, provider and dated version.

**Construct:** `specs/methodology/modeling-constructs.md § Constructs § Decision Table` \
**Conditions:** Reconciliation current?, Destination matches?

| Reconciliation current? | Destination matches? | External dispatch |
|---|---|---|
| false | - | Deny |
| true | false | Deny |
| true | true | Send only the input permitted for this call kind |

The Control plane admin can view the permitted call kinds.
