## Secrets management

Break-glass credentials ([`specs/application/technical/identity-and-access.md § Platform admin access`](/specs/application/technical/identity-and-access.md#platform-admin-access)) live in a secrets vault, never the structured database and never a config file. A secrets vault is the same class of infrastructure the customer likely already runs for their own secrets. PriceHorizon integrates with the customer's vault where one exists, rather than requiring a separate one. A database row or a config file would put a root-level credential inside the same backups, exports, and access paths as ordinary business data. That is the kind of blast-radius mixing this design avoids everywhere else. The vault provides what neither alternative does on its own: encryption specific to credential material, access to the credentials scoped to the break-glass process alone, built-in rotation, and an audit log of every retrieval. The audit log matters more here than almost anywhere else in the system, because break-glass access should be rare enough that every use is worth scrutinizing on its own.

The same vault holds every credential in the system, not only the break-glass one. The vault is the mechanism behind [`specs/application/product/platform-and-compliance-operations/deployment-topology.md § Deployment Topology`](/specs/application/product/platform-and-compliance-operations/deployment-topology.md#deployment-topology)'s promise that every credential PriceHorizon holds lives in an isolated vault. The IdP integration secrets that establish trust with the client's identity provider belong there, because forging or stealing one is equivalent to forging identity itself. The client's own credentials for any data source connection enabled through the control plane ([`specs/application/technical/control-plane-service/control-plane.md § Control Plane`](/specs/application/technical/control-plane-service/control-plane.md#control-plane)) belong there too. They do not sit in the structured database alongside the ordinary configuration that connection produces. The vault gives them the isolation [`specs/application/product/tenant-administration/data-source-connections.md § Data Source Connections`](/specs/application/product/tenant-administration/data-source-connections.md#data-source-connections) promises them.

Most structurally, the query, materialization, and control plane services each get their own separately issued database credential from the vault, scoped to that service alone. Within the query service, the vector database credential is scoped per business-unit namespace ([`specs/application/technical/data-model.md § Core Data Model`](/specs/application/technical/data-model.md#core-data-model)), not one flat credential for the whole store. The query service holds credentials only for the business-unit namespaces a query-user claim grants, so a bug in application code cannot reach a namespace it was never issued a credential for. These scoped credentials make the control plane service's exclusive write access to the reference tables ([`specs/application/technical/engineering-and-production-considerations.md § Engineering and Production Considerations § Service boundaries`](/specs/application/technical/engineering-and-production-considerations.md#service-boundaries)) an enforced fact rather than a policy statement. If every service drew from one shared, config-file-stored credential, the service boundary would be a diagram, not a control.

PriceHorizon reaches its vault through one adapter. The adapter has a provider for the stack's vault ([`specs/application/technical/stack.md § Technical Stack`](/specs/application/technical/stack.md#technical-stack)) and for each vault the customer's installation may use instead ([`specs/application/technical/environments.md § Environments § Customer Installation`](/specs/application/technical/environments.md#customer-installation)). The installation's configuration names the vault in use. So integrating with a vault the customer already runs is a choice of provider, not a change to the services that call the adapter. The adapter abstracts how a credential is retrieved, not what the vault guarantees. These guarantees are properties of the vault itself: encryption specific to credential material, access scoped to each service and, for the vector database, to each business-unit namespace, built-in rotation, and an audit log of every retrieval. Each provider therefore declares which of these guarantees its vault provides. An installation refuses to start on a vault lacking any of them, and names what is missing, rather than run with a credential less protected than this section requires.
