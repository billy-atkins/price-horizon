## Secrets management

Break-glass credentials (`specs/application/technical/identity-and-access.md § Platform admin access`) live in a secrets vault, never the structured database and never a config file, the same class of infrastructure the customer likely already runs for their own secrets, and PriceHorizon integrates with it where one exists rather than requiring a separate one. A database row or a config file would put a root-level credential inside the same backups, exports, and access paths as ordinary business data, exactly the kind of blast-radius mixing this design avoids everywhere else. The vault provides what neither alternative does on its own: encryption specific to credential material, access to them scoped to the break-glass process alone, built-in rotation, and an audit log of every retrieval, which matters more here than almost anywhere else in the system, since break-glass access should be rare enough that every use is worth scrutinizing on its own.

The same vault holds every credential in the system, not only the break-glass one, the mechanism behind `specs/application/product/platform-and-compliance-operations/deployment-topology.md § Deployment Topology`'s promise that every credential PriceHorizon holds lives in an isolated vault. The IdP integration secrets that establish trust with the client's identity provider belong there, forging or stealing one is equivalent to forging identity itself. The client's own credentials for any data source connection enabled through the control plane (`specs/application/technical/control-plane-service/control-plane.md § Control Plane`) belong there too, not in the structured database alongside the ordinary configuration that connection produces, the vault isolation `specs/application/product/tenant-administration/data-source-connections.md § Data Source Connections` promises them. Most structurally: the query, materialization, and control plane services each get their own separately issued database credential from the vault, scoped to that service alone, and within the query service, the vector database credential is itself scoped per business-unit namespace (`specs/application/technical/data-model.md § Core Data Model`), not one flat credential for the whole store, and the query service holds credentials only for the business-unit namespaces a query-user claim grants, so a bug in application code cannot reach a namespace it was never issued a credential for. This is what makes the control plane service's exclusive write access to the reference tables (`specs/application/technical/engineering-and-production-considerations.md § Engineering and Production Considerations § Service boundaries`) an enforced fact rather than a policy statement, if every service drew from one shared, config-file-stored credential, the service boundary would be a diagram, not a control.

PriceHorizon reaches its vault through one adapter, with a provider for the stack's vault (`specs/application/technical/stack.md § Technical Stack`) and for each vault the customer's installation may use instead (`specs/application/technical/environments.md § Environments § Customer Installation`), the installation's configuration naming the one in use, so integrating with a vault the customer already runs is a choice of provider, not a change to the services calling it. The adapter abstracts how a credential is retrieved, not what the vault guarantees: encryption specific to credential material, access scoped to each service and, for the vector database, to each business-unit namespace, built-in rotation, and an audit log of every retrieval are properties of the vault itself, so each provider declares which of them its vault provides, and an installation refuses to start on a vault lacking any, naming what is missing, rather than running with a credential less protected than this section requires.
