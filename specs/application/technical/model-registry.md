## Model registry

Elasticity models, competitor price-response models, forecasting models, the driver signal extraction model used on the qualitative corpus, the narrative rendering model used to turn a rationale into prose, the driver attribution weighting rubric, the confidence scoring weighting rubric, the simulate confidence weighting rubric, and the share-response, volume, and margin models used by simulation are all exposed as versioned, callable tools with documented inputs, outputs, confidence intervals, and a last-validated date. Each versions independently of the application and of every other model in the registry (`specs/application/technical/engineering-and-production-considerations.md § Engineering and Production Considerations`), so a forecasting model can be recalibrated without touching the elasticity model or the application logic that calls both. The narrative rendering model's version is tracked for the same operational reasons as the rest, so a quality regression is a traceable, rollback-able event, but it sits outside the numeric-determinism contract, as `specs/application/technical/query-service/layered-output-synthesis.md § Layered Output Synthesis (producing the answer) § Narrative rendering` scopes it. The reasoning layer calls these tools, it does not reimplement their logic. The quantitative models, elasticity, forecasting, price-response, share-response, volume, margin, are the right fit for a model registry of versioned artifacts with documented inputs and outputs, the one `specs/application/technical/stack.md § Technical Stack` names, rather than a custom-built abstraction. The LLM-based tools, driver signal extraction and narrative rendering, are narrower: both are schema-constrained generation, extraction into a bounded structure, rendering restricted to only the fields it is given, not open-ended reasoning, so a thin, provider-agnostic call layer, in process, the one `specs/application/technical/stack.md § Technical Stack` names, is the right amount of abstraction, a unified interface across model providers plus retry and fallback, without the chains, memory, and agent surface area a general LLM framework carries and this design has no use for.

A call reaches a language model in each of these kinds, each sending only its own input: the language model reasoning over a question (`specs/application/technical/glossary-and-grounding.md § Guaranteed grounding`), the question and the retrieved facts and model results it cites, the forecasts and Brand A's own targets among them; driver signal extraction (`specs/application/technical/materialization-service/driver-signal-extraction.md § Vector and semantic mapping, with structured extraction`), each qualitative document it reads, with the codes it resolves the document's entities and geographies to; narrative rendering (`specs/application/technical/query-service/layered-output-synthesis.md § Layered Output Synthesis (producing the answer) § Narrative rendering`), the rationale record it renders; embedding, a document's chunks as it is ingested (`specs/application/technical/materialization-service/driver-signal-extraction.md § Vector and semantic mapping, with structured extraction`) and a question's search text as evidence is retrieved (`specs/application/technical/query-service/intent-and-retrieval.md § Dynamic Retrieval and Weighting (when the question is asked) § Parallel evidence retrieval`); and semantic matching, reconciliation's fallback over product names (`specs/application/technical/materialization-service/reconciliation.md § Product and Geography Reconciliation`). Every one goes through the one call layer, by default to Acme AI's own models hosted in the installation. Reasoning over a question, driver signal extraction and narrative rendering may be served by a frontier model provider instead: the installation's configuration, held in a configuration object the client's own infrastructure team owns in the installation's Kubernetes namespace, which the deployment chart reads and no upgrade writes, whether Acme AI-managed or self-managed, names each kind a frontier provider serves, with the provider's dated model version; only those kinds' calls leave the installation, each carrying only its own input, and the version serving each call is recorded, Acme AI's own hosted model's and a frontier provider's alike: reasoning's and narrative rendering's in the provenance of the answer they serve (`specs/application/technical/data-model.md § Core Data Model § Pipeline and Answer Artifacts § Answer Provenance`), and driver signal extraction's on each signal it produces (`specs/application/technical/data-model.md § Core Data Model § Vector Database Schema § Driver Signal`), so an answer shows which models served it. Embedding and semantic matching never leave: a corpus is searched only with the model that embedded it, and matching runs over every catalog the installation holds. No quantitative model or weighting rubric is ever served outside the installation. A Control plane admin sees which kinds are named (`specs/application/technical/control-plane-service/control-plane.md § Control Plane`); and as the installation starts, before any call reaches a frontier model provider, the control plane service records a change from the set it last recorded as one frontier_models_changed entry for the installation, with the kinds and versions named before and after it (`specs/application/technical/data-model.md § Core Data Model § Audit Log § Audit Log Entry`), and while it cannot, no call reaches one. This carries out `specs/application/product/platform-and-compliance-operations/deployment-topology.md § Deployment Topology § Frontier Models`.

`specs/application/technical/architecture.md § Architecture Overview § Diagrams § Layer Composition`, `specs/application/technical/architecture.md § Architecture Overview § Diagrams § From Evidence to Answer` and `specs/application/technical/architecture.md § Architecture Overview § Diagrams § Trust Boundaries` render this.
