# Auditing the specifications

The methodology and `specs/AGENTS.md` govern the files in Spec of Record's scope, as `specs/methodology/scope/what-spec-of-record-governs.md § What Spec of Record Governs` sets. This skill reads no code. Checking that those rules held splits into separate jobs.

A script decides whether a citation resolves, whether a front matter list is sorted and whether a fenced block is well-formed. Everything that has gone wrong here was a statement that resolved perfectly and was wrong anyway. A blueprint omitting the security control its own directory calls primary passes every mechanical check ever written.

The audits are the substance. The script is a pre-pass.

    python .ai/skills/audit-specs/scripts/audit-specs.py --check-scope                 # from the repo root
    python .ai/skills/audit-specs/scripts/audit-specs.py --check-scope --root <path>   # an explicit root
    python .ai/skills/audit-specs/scripts/audit-specs.py --check-scope --sub-scope core-canon documentation  # only the findings in those sub-scopes' files
    python .ai/skills/audit-specs/scripts/audit-specs.py --list-candidates             # places for the reading audits that use them
    python .ai/skills/audit-specs/scripts/audit-specs.py --list-candidates --detail    # every Clear Prose candidate, not only their count for each file
    python .ai/skills/audit-specs/scripts/audit-specs.py --check-layout .ai/follow-ups.md  # the checks of a block of fields and of a blank line, for the Working-file form audit

Run the script first, because it is fast and because its findings would otherwise be noise in a reading pass.

## These audits assume an agent

Each audit requires a judgment the files do not encode, often across a whole directory held in mind at once. A script cannot judge whether a summary is still true. A person can, but a person does it by sampling, with attention that degrades across a long directory. Reading a whole unit in one pass and holding it together is what makes a method this exhaustive worth writing down rather than aspiring to.

## Workflow

A run follows this Workflow's steps, and each audit follows the ones it needs.

**Start from the entry point.** Read `specs/AGENTS.md`, then `specs/methodology/glossary/glossary.md`, and a directory's `index.md` before working in the directory, as `specs/methodology/scope/progressive-disclosure.md § Progressive Disclosure` and `specs/methodology/scope/what-spec-of-record-governs.md § The Shape of the Scope` have it.

**Fork on the kind of specification.** Each audit's Kind column names the kinds of file the audit reads, by the values `specs/methodology/checks.md § Check` gives a check's Reads: a kind of change, `fixture-files` for the fixture files of the kept tests, or `working-files` for the working files, which are of no kind (`specs/methodology/working-files/main.md § The Working Files`). `specs/methodology/scope/what-spec-of-record-governs.md § What Spec of Record Governs` sets what each value takes in, and has an audit read a fixture file only where its Kind names `fixture-files`. `.ai/skills/audit-specs/references/canon-specs.md` holds the audits written for the canon, and `.ai/skills/audit-specs/references/app-specs.md` those written for the application specs. A run given `--sub-scope` names one or more of the sub-scopes `specs/methodology/design-workflow/designs-reviews.md § A Design's Reviews` defines, each a set of files, and a run given none is the full run. A run picks its audits, and what it reads of each audit's unit, as that section has it. `--sub-scope` is the script's argument too: the script's pre-pass runs whole whatever the sub-scopes, and reports only what lies in their files, as `§ What the script checks` has it. A run names no design, as `specs/AGENTS.md § Design, Refactor, Refine § An Audit` has an audit.

**Make each reading as the methodology has it made.** `specs/methodology/semantic-check-methods/main.md § Semantic Check Methods` says what every reading shares: reading the files in full, reading a passage beside its source, and using a candidate list. ## The report

A run states the unit it covered and gives a verdict on it: current, current with named fixes, or drifted. A run in a design's apply reports its findings as any run does, and the builder triages them against the design's changes, as `specs/AGENTS.md § Design, Refactor, Refine § An Audit` has an audit read. Each finding is a row, in the shape this section gives for its kind of defect.

**Construct:** `specs/methodology/modeling-constructs.md § Constructs § Decision Table` \
**Conditions:** Defect

| Defect | Row |
|---|---|
| A summary disagrees with what it summarizes | the file, the claim, the source, and which compression distortion it is |
| A required thing is absent, or sits on the wrong side | the location, the rule it breaks, and what is missing or misplaced |
| A rule has two homes | both statements, the home chosen, and, where it was hoisted, the usages that forced its height |
| Any other rule broken | the location, the rule it breaks, and what is wrong |

A report carries the warnings the script listed for its unit, under a heading of their own. Each warning is a rule the specs record as kept by nothing. A warning is listed, and is never a finding. A report also carries what was examined and declined: the candidate that had the shape of a defect and turned out not to be one, with the reason it failed the test. This record is neither padding nor optional. The expensive half of an audit is arriving at the judgment that something suspicious is correct. A report that keeps only the findings throws that half away, so the next run pays for it again and may reach the opposite answer. Declining a candidate in writing is also what makes an over-eager audit reviewable: a reader can check a rejection as easily as a finding.

A report carries its review observations (`specs/methodology/glossary/glossary.md`) apart from its findings, under a heading of their own and uncounted: what the auditor noticed beyond the audits it ran. A run in a design's apply has the builder bring each to the user with its triage, as `specs/AGENTS.md § Design, Refactor, Refine § Who Decides` has it.

Each run writes one file to `.ai/tmp/audit-specs/`, named for the unit and the date. A run clears any earlier report for the same unit. That earlier report is stale output, which a skill cleans as `specs/methodology/working-files/main.md § The Working Files` has it.

A finding in a working file's form is put right as `specs/methodology/working-files/main.md § The Working Files` has the file changed. In a design's apply, its builder settles each other finding as `specs/AGENTS.md § Design, Refactor, Refine § An Audit` has an audit's findings settled. Outside a design's apply, any other finding becomes a design document (`specs/methodology/working-files/main.md § A Design Document`) rather than an edit. The design goes through the Design, Refactor, Refine process (`specs/AGENTS.md § Design, Refactor, Refine`). `specs/AGENTS.md § Design, Refactor, Refine § Direct Edits` says when a small finding may be applied directly instead.

## Running one

`specs/AGENTS.md § Design, Refactor, Refine § An Audit` covers who reads an audit's findings, how their quoted evidence is confirmed and how they are triaged. Who runs an audit and what the audit reads are as `specs/AGENTS.md § Design, Refactor, Refine § Who Checks What and Why § Check Roles [Check: an audit]` has them: a cold agent given this skill's name and, in a design's apply, as its `--sub-scope`, the sub-scopes the user settled, as `specs/methodology/design-workflow/designs-reviews.md § A Design's Reviews § The Sub-scopes a Design Settles` has them settled, with no brief (`specs/methodology/design-workflow/reviews-brief.md § A Review's Brief`). All of it applies. Here, an audit run by the content's own author costs a confident sweep that misses the section the author forgot existed.

## What the script checks

Each row describes, in the script's own terms, what the script checks for the section the row names. That section governs the check (`specs/methodology/scope/rules-and-skills.md § Rules and Skills`). A check that lists a warning reports what the specs record as a gap of the system: a Constraint that nothing keeps. The script prints its warnings after its findings, apart from them. A warning never sets the script's exit status, so a run listing warnings alone passes. Each check is a unit of its own in the code the skills share, taking one file's path and text, a file's with the scope it resolves against, or the scope whole, which the script reads from its root once and hands to each. Each unit carries a canon-spec annotation citing each section of its row that its part of the check enforces, or its check's record where it has one, as `specs/methodology/skills/authoring-a-skill.md § Authoring a Skill` has a unit carrying out a check cite it, so a kept test holding the check finds it by that citation. The construct checks run as the scope is read, each a unit of their own code with its own annotation, and one unit hands their findings to the script, citing nothing, since it carries out no check.

## What is deliberately not audited

**Script checks were built and removed.** They were removed for the reason `specs/methodology/scope/rules-and-skills.md § Rules and Skills` gives. "Every product capability section has a `Test Scenarios` child": "is this a capability" is a judgment the files do not encode, and most of its findings were overview or definitional headings. "Every `Given` names a role the product specs define": the rule is real, but absence does not decide a violation. A scenario about system state has no actor, and a scenario may name its role in the `Then`. Scenario coverage now covers both by reading.

**Migration fidelity gets no audit.** Comparing a migration's source statements against their rewritten destinations is exactly this kind of work. Yet migrations are rare enough that a written method would be exercised about once, and one exercise is not enough to generalize a method from. Brief the comparison directly when a migration happens.

## Traps worth knowing

**Lineages start below the file's title.** `specs/methodology/sourcing-and-citation/writing-a-citation.md § Writing a Citation` states this. Building lineages from level 1 down was the script's earliest defect. It made every same-file citation in the repo fail at once, and it looked like a wall of broken citations rather than one bad assumption.

**Not every backtick span containing a section token is a citation.** A rule that discusses the token, or shows a forbidden heading form as an example, mentions the token rather than using it. The script treats only a span in one of the citation shapes as a citation:

```
§ Title
path/to/file.md § Title
§ Title [Key: value]
path/to/file.md § Title [Key: value; Key: value]
```

The script leaves every other span alone. Before it looks for a token outside a span, it strips every inline span. This skill's own documentation tripped that check on its first run. That is the most direct evidence available that the distinction is needed.

**A fenced block's content is set aside unless a check's row says it reads the block.** A citation shown inside a fenced block is an illustration, and the citation checks do not read it. A check reads inside a fence only where its row in `§ What the script checks` says so: the rows on a `gherkin` block, a `mermaid` block, the scope's tree and a `markdown` block, which is read as a file of its own, as `specs/methodology/spec-style/markdown.md § Markdown` has it.

**A mermaid block does not begin with `flowchart`.** Every diagram in this repo opens with a `config` front matter block inside the fence, so a check reading the first line fails on correct content. Match anywhere before the first node.
